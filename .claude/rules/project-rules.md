# Project Rules

Durable rules for AI dev + code-review agents working on this project. Rules are accumulated from completed epic retrospectives and any other moment where a general pattern is recognized. Each rule captures a reusable lesson, with a short citation of the bug, anti-pattern, or situation that motivated it.

**How rules land here:** every retrospective ends with a "Rules to codify" step. Any lesson with general-pattern shape (would prevent a recurrence of a class of issues in a future epic, not just the specific incident at hand) is added to this file. Narrow one-off fixes stay in the source retro/story document and do NOT become rules.

**Template usage:** this header and Rule #1 (the meta-rule below) are intentionally project-agnostic — they can be dropped into any new project's `.claude/rules/project-rules.md` as the starting template. Subsequent rules (#2 onwards) are project-specific and accumulate from that project's retrospectives.

---

## 1. Meta-rule — codify retrospective lessons as rules

**Context:** Every completed epic retrospective (and any other moment a reusable lesson is explicitly identified).

**Rule:** At the end of every retrospective, add a "Rules to codify" step. For each lesson with general-pattern shape, append a new rule to this file following the format below. Narrow one-off fixes stay in the retrospective document and do NOT become rules.

**Format per rule:**
- Numbered heading with short title
- `**Context:**` — when the rule applies
- `**Rule:**` — what to do (or not do)
- `**Why:**` — the bug, anti-pattern, or cost that motivated the rule (with commit hash or bug number from the source retro if useful)
- Optional code snippet or example

**Why:** Retrospectives without a codification step produce lessons that age. The next epic then re-learns them the hard way. The value of a retro compounds only when its lessons become durable guidance the next dev/review agent actually sees before making a decision. Story files, commit messages, and retrospective prose do not survive as agent-visible context beyond the session that wrote them — `.claude/rules/*.md` does.

**How to apply:** when closing any retrospective:
1. Review the retrospective's "What could've gone better" and "Lessons learned" sections.
2. For each lesson, ask: *does this prevent a class of future bugs, or is it specific to the one that already happened?*
3. If class-of-bugs → append to this file.
4. Commit the rule file update in the same commit as the retrospective document.

**Cross-project library note:** rules here are project-scoped by default. When multiple projects adopt this system, rules with evidence from 2+ projects can be elevated into a shared library (shared npm package, git submodule, or copy-and-curate sync). Tag rules with `id:` slugs and `scopes:` frontmatter when that cross-project moment arrives so merging is mechanical rather than manual.

## 2. ~~Build cross-package `dist/` before running cross-package tests~~ — SUPERSEDED (Story 3.0)

**Status:** SUPERSEDED by Story 3.0 (2026-05-31). The build-first dance is **no longer required** for tests. Story 3.0 (AC #1, deferred-work 2.4) added a `resolve.alias` to the root `vitest.config.ts` mapping each `@agentbbs/<pkg>` specifier to that package's `src/index.ts`, so cross-package tests now resolve against **live TypeScript source**, not each package's built `dist/`. A brand-new `core` export is visible to `mcp-server`/`cli`/`ui-shared` tests with **no prior `pnpm run build`** (proven by `packages/mcp-server/src/cross-package-alias.proof.test.ts`).

**Heading retained (not deleted)** so existing references (`deferred-work.md`, the Epic 2 retro, Story 3.0) don't dangle.

**Residual guidance — the build is still the `dist`-artifact guard, NOT a test prerequisite:** because tests now run against `src`, the test suite does not validate the shipped `dist`/`exports` artifact. Keep `pnpm run build` in the gate so a broken barrel `exports` still surfaces at build time. The alias maps package **roots** only (object-form exact match); if a test ever imports a deep `@agentbbs/<pkg>/<subpath>` specifier, alias that subpath explicitly too (none do today).

**One exception — forked cross-process tests still need `dist`:** the Vitest `resolve.alias` only governs imports resolved *inside* the Vitest process. The cross-process suites (`packages/data-access/src/register-race.test.ts`, `concurrency.test.ts`) `child_process.fork` a BUILT worker (`dist/*-worker.js`) that runs as a real Node process and resolves `@agentbbs/core` via the package `exports` → `dist` (NOT the alias). So when you add a `core` export that a forked worker consumes, you MUST `pnpm run build` first — and because `tsc -b` is incremental, a deleted/stale `core/dist` needs `--force` (or a cleaned `.tsbuildinfo`) to actually regenerate, else the worker dies with `ERR_MODULE_NOT_FOUND` and the test reports `worker N exited code=1`. Evidence: surfaced during the Story 3.0 lead smoke — deleting `core/dist` to prove the alias left the forked workers unable to resolve core until a forced rebuild. The standard gate (`pnpm run build` before `pnpm test`) covers this; the caveat matters only when iterating tests without a build.

**Historical motivation (why this rule existed):** Recurred across Epic 2 — the Story 2.4 dev hit a false-red `INTERNAL_ERROR` in the `mcp-server` integration tests because `core/dist` predated the new `updateFocus`/`NO_IDENTITY` exports; 2.5 and the per-story stdio smokes had to build-first for the same reason. It read as a real failure but was pure staleness. Rule 2 itself flagged the Vitest `resolve.alias` as the preferred permanent fix and said to supersede on landing — which Story 3.0 did.

## 3. Verify version-specific external API against the INSTALLED type definitions, not just web search

**Context:** Implementing against any third-party library/SDK/framework whose API is version-specific, when you are not 100% certain of the exact current signature (the Research-First trigger in `.claude/rules/research-first.md`).

**Rule:** Treat the **actual installed package's published types** (`node_modules/<pkg>/**/*.d.ts`) and the **official docs/source pinned to the installed version tag** as the authoritative source for signatures, parameter order, accepted input shapes, and return types. Use web search / Perplexity for discovery and trade-offs, but when a search result asserts a concrete API shape, **confirm it against the installed `.d.ts` before coding to it** — and when they disagree, the `.d.ts` wins. Record the verified signature (and any delta from what search claimed) in the story's Dev Notes / Dev Agent Record so the next agent doesn't re-litigate it.

**Why:** Epic 2 Story 2.1. A Perplexity pass on `@modelcontextprotocol/sdk@1.29.0` returned several confidently-wrong claims — that `registerTool` takes the tool name *inside* the config object, that you must hand-convert Zod to JSON Schema, and that you connect via `transport.listen(server)`. The published `dist/esm/server/mcp.d.ts` showed the opposite: name is a separate first argument, `inputSchema` natively accepts a Zod-4 raw shape / Standard Schema, and you connect via `await server.connect(transport)`. Coding to the search answer would have produced an API that does not compile, then a confused debugging loop. The installed types are generated from the exact code that runs — they cannot be out of date or hallucinated. (This sharpens, and is consistent with, `research-first.md`'s "confirm API and method signatures … prior to implementing".)

## 4. Verify a story's "Source facts" about EXISTING repo symbols before coding to them

**Context:** A story's Dev Notes assert that some internal symbol already exists — an error code, an event type, a function/type, a `file:line` reference, an exported name. Especially when the story was lead-authored quickly rather than via the full create-story artifact pass.

**Rule:** Treat every story Source-fact about EXISTING code as a **claim to confirm against the repo**, not a given. Before relying on "X already exists at `file:line`" / "the closed set already has CODE Y" / "helper Z is exported", `grep`/read the cited location. If the claim is wrong, make the smallest faithful additive correction (e.g. append the missing error code to the closed set — non-breaking), implement the story, and surface the corrected premise loudly in the Dev Agent Record / Change Log. This is the **internal-codebase analogue of Rule 3** (which covers external APIs): the same "don't code to an unverified asserted signature" discipline, applied to the project's own surface.

**Why:** Epic 4 Story 4.5. The lead-authored story claimed `HANDLE_NOT_FOUND` was "already in the closed set at `errors.ts:29`" — but line 29 was `BOARD_NOT_FOUND`; the code did not exist. The dev grepped, found the claim false, added `HANDLE_NOT_FOUND` additively (correct + non-breaking per the error-contract policy), and surfaced it. No harm done — *because the dev verified*. A confidently-wrong source-fact about an existing symbol can otherwise mis-scope a story (code to a missing import, assume a wrong shape) and produce a confused failure. Lead-authoring stories for speed is fine; skipping the dev-side verification of their asserted facts is not.

## 5. A concurrency-claiming AC requires a genuine cross-process race test — sequential coverage does not satisfy it

**Context:** A story has an AC asserting concurrent/parallel behavior ("two X arrive concurrently", "no lock, no error", "both land", "exactly one wins", "dedups to one"). The op may be a plain `append` OR an `appendGuarded`.

**Rule:** Prove the concurrency AC with a **genuine forked cross-process race** (mirror `packages/data-access/src/*-race.test.ts` / `concurrency.test.ts` — fork N real OS-process workers against a built `dist` worker, an IPC start-barrier, all hitting the real SQLite ledger), not merely a sequential `await a; await b` test. "It's a plain append, there's no `appendGuarded` contention to stress" is **not** a sufficient reason to skip it — the load-bearing guarantee is usually a *read-side derivation under concurrency* (a min-`seq` activator, a benign double-write that must dedup) that no sequential test exercises. The QA stage owns this; the dev should not defer it away.

**Why:** Epic 4 Stories 4.3 + 4.5. The dev twice argued the plain-`append` `reply`/`add_participant` ops needed no race beyond the sequential proof. QA overrode both; the forked races caught real, otherwise-untested guarantees — the `reply` activator min-`seq` derivation under an 8-way race, and the benign concurrent double-`board.joined` / double-`room.participant_added` collapsing to exactly one member/participant (empirically confirmed 8/8 raw double-writes → 1). Epic 1's `concurrency.test.ts` did NOT cover these (it only stresses `identity.seen`). Sequential tests pass while the real contention behavior stays unproven.

## 6. When a tool result contradicts committed/known state, verify against git ground-truth before acting

**Context:** Any agent stage (dev, QA, review, lead) receives a tool result that is surprising or inconsistent with what was just committed/observed — a file `Read` showing code that "shouldn't be there", a diff that doesn't match the changeset, a test failure referencing code nobody wrote, a batch of cancelled/garbled results.

**Rule:** Before acting on a surprising tool result — *especially* before editing code or recording a finding based on it — **confirm it against git ground-truth**: `git show <sha>:<path>`, `git diff HEAD -- <path>`, `git status --short`, `git log --oneline`. If the tool result disagrees with git, trust git and discard the phantom. Never apply a code change or log a defect whose entire basis is an unverified surprising read.

**Why:** Epic 4 Story 4.5 code review. A corrupted tool result fed the reviewer a fabricated `Read` of `append.ts` showing code that does not exist; the reviewer "found" a SQLite concurrency defect and began applying an `.immediate()` fix — then caught it via `git show`/`git diff` (the file was unchanged) and fully reversed it (the lead independently re-confirmed `git diff HEAD -- append.ts connection.ts` was empty before committing). A phantom tool result that survives into a code edit or a logged finding corrupts the changeset and the audit trail; git is the authoritative state.

## 7. Mutation-test a high-stakes semantic test to confirm it is not vacuous

**Context:** Adding a test that pins an easy-to-get-wrong SELECTION / ORDERING / PRECEDENCE / boundary semantic of a marquee feature (e.g. "the highest-`seq` live-👍'd message is the contract", "the min-`seq` reply is the activator", a tie-break, a sort key). Especially in the QA stage.

**Rule:** Once, before trusting such a test, **mutation-test it**: temporarily change the production code to a plausible WRONG implementation (e.g. "most reactors wins" instead of "highest seq", flip a comparator, off-by-one a boundary) and confirm the new test goes RED. Then revert the production code **byte-identically** (`git diff` on it must be empty) and confirm the test is green again. A test that passes against BOTH the right and a wrong implementation is vacuous and guards nothing. Do this for the core semantic of a marquee feature — not for every test (it has a cost).

**Why:** Epic 5 Story 5.3. The QA stage temporarily mutated `currentContract` (`contract.ts`) to a "most live reactors wins" selector and confirmed BOTH its new tests (highest-`seq`-not-most-reactors; ≥3-level reversion) went red — proving they discriminate, not merely pass — then reverted `contract.ts` byte-identically. This is the same class the Story 1.3 retro flagged (vacuous type assertions that pass regardless of correctness because Vitest ran them as runtime no-ops). A green test that does not fail when the code is wrong provides false assurance on exactly the load-bearing logic.

## 8. When a story's AC contradicts an earlier story's IMPLEMENTED design, reconcile explicitly — don't blindly implement it

**Context:** A later story's AC (from a planning doc authored before implementation) conflicts with the behavior an EARLIER story already shipped and proved — e.g. a gate the earlier story deliberately does not apply, a field shape since changed, an error the earlier design replaced with a side effect.

**Rule:** Do NOT mechanically implement the new AC over the established, shipped reality. STOP, determine which is correct (the implemented design is usually the ratified truth; the planning doc predates it), and **reconcile explicitly**: document the resolution in the story's Dev Notes / a "Design decision", adjust the AC's intent to fit the real surface, and surface it to the reviewer. If the earlier design is genuinely wrong, that is a `correct-course` change to the earlier surface — not a contradictory bolt-on in the new story. Either way the contradiction is resolved on purpose, in writing, never silently.

**Why:** Epic 5 Story 5.1. The epics.md AC said "a non-participant who posts a message → `NOT_A_MEMBER`", but Story 4.3 had already shipped `reply` as "acting = joining" (it GRANTS participation, by design, for the open-negotiation property). Blindly adding a `NOT_A_MEMBER` gate to `reply` would have broken Epic 4. The lead reconciled it in the 5.1 Dev Notes (the room-message post grants; the `NOT_A_MEMBER` gate the AC references is `post_announcement`'s sub-board gate, reaffirmed) instead of implementing the contradiction. BMad planning docs are written before implementation, so later-story ACs WILL sometimes contradict earlier-story reality; resolving it silently in either direction ships a defect.

## 9. Defer a performance/cost concern to its NAMED-CONSUMER story for measurement — not prematurely, not indefinitely

**Context:** Code review (or dev) surfaces a performance/cost concern (an extra read, an O(n) fold, a double-query) on a path whose real hot-path CONSUMER does not exist yet — so it cannot be sensibly measured or optimized at its origin.

**Rule:** Do NOT optimize it now (premature optimization, often the wrong tuning before the access pattern is real). Instead defer it in `deferred-work.md` with the explicit NAMED consumer story that will exercise the hot path ("→ Story X.Y, the `check` consumer"). When that consumer lands, it MUST actually MEASURE the cost (real timing at a representative scale) and CLOSE the item with evidence — either "measured, acceptable at V1" (close won't-fix-with-evidence) or a contained, behaviour-identical optimization. Never carry a perf item forever unmeasured, and never optimize it before its consumer exists.

**Why:** Epic 6 Story 6.1. Items 3.0-b (the `recordSeen` guard-before-append double-read) and 4.6-a (the `roomJoinSeq`/`roomMessagesSince` per-call full-stream fold) were flagged at the Story-3.0 / Story-4.6 code reviews and pointed at "Story 6.1, the `check` hot-path consumer". They were carried untouched for 2–3 epics (no premature optimization with no real access pattern), then Story 6.1 measured the actual per-call fold cost over the real SQLite ledger and applied a contained ~8× optimization, closing both with evidence. This avoided BOTH the class of premature optimization (tuning `recordSeen` before `check` existed) AND the class of silent perf debt (a perf concern that ships unmeasured because no story ever owned measuring it). The "→ named consumer" pointer in the deferred-work entry is what makes the measurement actually happen.

## 10. An open-source-facing or agent-CONSUMED doc/asset must ship a content-guard test pinning its machine-relevant claims to the code

**Context:** Authoring a doc or asset that a machine (an agent, a downstream installer, a contract consumer) relies on — a tool/API contract, a protocol spec agents follow, a prompt snippet inlined into an agent's system prompt, an event/error vocabulary doc. Distinct from prose docs a human merely reads.

**Rule:** Ship the doc WITH a content-guard test that pins its machine-relevant claims to the code's SOURCE OF TRUTH — not a hand-copy. Pin tool names to the live `McpServer.listTools()`; error codes to `BOARD_ERROR_CODES`; events to `EVENT_TYPES`; named moves/semantics to the documented constant; the referenced-tools of an inlined snippet to the live tool set. Parse the machine-relevant part from a clearly-delimited block (a sentinel pair like `AGENTBBS-*:BEGIN/END`, or a section-scoped table) so the parse is robust and prose mentions don't false-positive. Mutation-test the guard (Rule 7): a drift (a dropped name, a renamed code, a phantom tool added to the inlined block) must turn it RED. A doc that silently lies about the code is worse than no doc; for an agent-consumed asset (a prompt snippet the install kit inlines verbatim), a phantom tool becomes a runtime failure the agent hits.

**Why:** Epic 7. The tool contract (7.0), the Negotiation-Protocol doc (7.1), and the agent-prompt snippet (7.3) each shipped a content-guard pinning their claims to code (names↔`listTools()`, codes↔`BOARD_ERROR_CODES`, events↔`EVENT_TYPES`, the four moves + the FR21 "highest-`seq` live-👍'd" semantic, the snippet's tools↔the live set). In THREE of the four, the QA stage extended the guard and caught a REAL gap the dev's guard missed: the §5 event-vocab pin (7.0), the FR21-semantic pin (7.1 — a "most 👍s" rewrite passed every other guard), and the "no phantom tools" pin (7.3 — a fake tool inlined into an agent prompt). Each was mutation-tested non-vacuous. Without the code-pin, an open-source contract or an agent-configured snippet drifts the moment the surface changes, and nobody notices until an agent calls a tool that no longer exists.

**Epic 8 reinforcement (the call-form blind spot):** the content-guard's phantom-tool regex must match the asset's ACTUAL invocation style. Story 8.1's guard used `` /`([a-z][a-z_]{2,})`/g `` (token + closing backtick only); the asset wrote its calls as `` `register{ handle }` `` (a `{` follows), so a phantom introduced only in call-form slipped GREEN (reviewer-proven). Broadened to `` /`([a-z][a-z_]{2,})(?:`|\{)/g ``. When you mutation-test a tool-name guard, mutate a token in EVERY form the asset uses it (bare and call-form), not just one. Corollary: a guard that false-positives on the author's own non-tool prose (a backticked `curl`, a server name, a JSDoc word) is the guard WORKING — fix by rewording the prose or minimally allowlisting the genuinely-non-tool token, NEVER by weakening the scan.

## 11. An agent-executed asset's SAFETY-CRITICAL procedure must be an extractable, executable unit — proven by running the asset's OWN code

**Context:** Shipping an agent-executed asset (an installation kit, a migration runbook, a generator) that performs SAFETY-CRITICAL DETERMINISTIC file/state surgery in a target the author does not control — idempotent edits, backup-before-overwrite, never-touch-foreign, key-scoped merges. Distinct from a pure documentation/claims asset (that is Rule 10's domain).

**Rule:** Do NOT describe the safety-critical procedure in prose for the agent to hand-implement each run. Ship it as an INLINE, EXTRACTABLE, EXECUTABLE unit inside the asset (e.g. a fenced ```js helper exporting the operations), have the agent INVOKE it, and PROVE its properties by EXTRACTING + IMPORTING + EXECUTING the asset's OWN code against real temp fixtures — never a test re-implementation. The proof must cover, at minimum: idempotency (re-running identical content is a byte no-op, no spurious backup), backup-before-overwrite (a real change makes a timestamped backup first), and never-touch-foreign (planted foreign assets — including the project's other installation kits — survive BYTE-IDENTICAL; for JSON, foreign keys/values preserved). Mutation-test it non-vacuous (Rule 7): defeating the idempotency short-circuit, or dropping foreign data, must turn the safety test RED.

**Why:** Epic 8 Story 8.4. The `install-agentbbs.md` kit writes files in a stranger's BMad project; its idempotency / timestamped-backup / never-touch-foreign (incl. the project's `epic-cycle` kit) / `.mcp.json` key-scoping are load-bearing — a bug corrupts a consumer's repo. The kit ships an inline `applyBlock`/`mergeMcpServer` Node helper and the safety test extracts + imports + executes THAT exact helper against temp files (planted `epic-cycle` file + foreign MCP server + unrelated key all survive byte-identical; re-runs are byte no-ops; changes back up first), mutation-tested RED on a defeated idempotency short-circuit and a dropped foreign server. A safety-critical procedure described only in prose is re-derived (possibly wrongly) on every agent run and cannot be regression-tested; making it an extractable executable makes it deterministic at install time AND testable on the asset's own instrument. This extends Rule 10 (which pins what an asset SAYS to the code) to what an asset DOES.
## 12. A UI/web story's per-story smoke MUST drive a REAL browser — DOM-shim tests (jsdom/happy-dom) are necessary but NOT sufficient

**Context:** Any story shipping a browser-rendered surface (a component, a page, a client that consumes an HTTP/SSE host) whose load-bearing behavior includes CSS-custom-property resolution, CSP-relevant output, real network (fetch/`EventSource`/no-network), or focus/paint. Distinct from a pure node/library story.

**Rule:** The automated tier may run under a DOM SHIM (jsdom/happy-dom) — that is correct for fast component tests — but the lead's per-story SMOKE MUST exercise the deliverable in a REAL browser (chrome-devtools-mcp): load the actual built artifact/host, read computed styles / network log / a planted canary out-of-band, not just assert against the shim. DOM shims resolve `var()` substitution into computed `color`, CSP/inline-style enforcement, real `EventSource` SSE delivery, and real network requests INCOMPLETELY or not at all — a green shim test can hide a real-browser failure (and a real-browser pass is the load-bearing NFR evidence for things like NFR12 inert rendering or live SSE). Corollary (monorepo): when the repo uses a single root test-runner config with a `projects`/multi-environment split (e.g. a `*-dom` happy-dom project + a node project), the CANONICAL gate is the ROOT test command (`pnpm test`), NOT a per-package run — a per-package `vitest` invocation bypasses the root DOM-project mapping and FALSELY reports `.tsx` DOM tests as failing (`document is not defined`). Use git/the root command as ground truth before reading a per-package failure as a regression (Rule 6).

**Why:** Epic 9 (the first UI epic). Every story's real-Chrome smoke proved something the happy-dom suite structurally could not: 9.1 the token core's `var()` flip dark→light actually PAINTS in a real browser (happy-dom does not reliably substitute `var()` into a child's computed `color` — the dev had to assert the custom property at its declaration site instead); 9.2 the NFR12 inert pipeline fires ZERO content-triggered network requests + no script in REAL Chrome (the canary never fires) — the load-bearing security evidence; 9.3/9.9 a real `EventSource` receives the SSE delta the host pushes (Mode A live fold); 9.6 the FR21 agreed mark actually moves in the DOM. Separately, THREE different agents (9.6/9.9/9.10 reviewers) nearly mis-read `.tsx` DOM tests as failing because `npx vitest` inside `apps/web` bypasses the root `ui-shared-dom` happy-dom project — the canonical `pnpm test` was green every time. A UI epic that smokes only against the shim ships unverified real-browser behavior; one that reads per-package test runs as the gate chases phantom failures.

## 13. A thin client (UI/host/extension) must add only CLIENT-LAYER fields and map its affordances to EXISTING board ops — never mutate the ratified agent contract, never fabricate a board op

**Context:** Building a thin client over the shared core (the web host, the web UI, the VS Code extension/webview, any future consumer) that needs (a) a field the ratified agent-facing contract does not carry, or (b) an action/affordance whose obvious shape isn't an existing board op. Distinct from changing core/the agent surface itself (which is a deliberate, drift-guarded contract change).

**Rule:** When a client needs a field the ratified contract lacks, add it at the CLIENT/HOST layer (a display-only / host-surface field) and keep the drift-guarded agent contract (core types, MCP wire, error set) BYTE-IDENTICAL — verify the contract drift-guards stay green and the relevant core/MCP source is unchanged. When a client needs an action, map it to an EXISTING board op honoring the shipped semantics (grant-on-act, append-only/no-leave, open-read, participation-vs-membership gates) — do NOT invent a board op the ledger does not support, and do NOT create a client-only backdoor that bypasses core. If the client genuinely needs a NEW capability the board lacks, that is a core/contract change or a new story — surface it (Rule 8), don't smuggle it into the client. A visible affordance whose underlying op is deferred must be gated (disabled/handoff) OR explicitly recorded as an inert stub in `deferred-work.md`, never left as an unrecorded clickable no-op.

**Why:** Epic 9. (a) Story 9.5 needed a per-post DISPLAY timestamp, but `RoomMessage`/the ratified MCP message wire intentionally carry no `createdAt` (seq is the order key) — the dev added `created_at` HOST-LAYER-ONLY on `/api/rooms/:id`, leaving core + the MCP `read_room`/`check` wire byte-identical (drift-guards green); 9.6 added `NO_OPERATOR` as a HOST-surface error code, NOT in core's closed `BOARD_ERROR_CODES`, preserving the 10-code agent contract. (b) Story 9.7 reconciled "join room to post" against the shipped grant-on-act model (`reply` grants room participation; there is no standalone room-join op) → `[ join room to post ]` = `joinBoard` + the field, SEND = `reply`; 9.8 made "close a tab" a VIEW-only action because the board has NO leave/un-participate op (append-only membership) — neither invented a contradicting op or an operator backdoor; the operator posts via the SAME core `reply` an agent uses. (c) The Epic 9 retro then found the operator's INITIATE surface (create project / post announcement / proactively join) genuinely absent — correctly NOT smuggled into the client as a backdoor, but named as a follow-up `/bmad-correct-course` parity epic; the `＋ join a project…` row was left visible per AC but recorded in deferred-work as an inert stub (9.4-join-project-inert). Extends Rule 8 (reconcile later-story ACs vs shipped design) and Rule 10 (pin claims to the code's source of truth) to client/host surfaces — the rule the upcoming VS Code extension (another thin client over the same core) will lean on most.

## 14. A multi-story user FLOW needs an end-of-epic INTEGRATED exploratory smoke — per-story AC smokes miss the seams

**Context:** An epic that ships a user-facing FLOW spanning multiple stories, where each story implements one slice of a single journey (e.g. create → browse → open → respond). Distinct from an epic of independent features.

**Rule:** After the last story's per-story smoke and BEFORE the epic merge, the lead runs a FREE-FORM exploratory smoke that drives the assembled product like a real user across the WHOLE flow — NOT scripted to any one story's ACs. Poke the seams: create something in story A, then try to find/open/act on it via the surface story B built; use affordances in combinations no single story owns. The entire automated pyramid (unit / DOM / host-integration / per-story smoke) is AC-SHAPED — every layer asks "did THIS story do what it said?", none asks "is the integrated surface whole between stories?" Seam and parity gaps live in that space and pass every green tier. Record the exploratory smoke as its own gate; a gap it finds is HIGH (a real user would hit it), handled like a failed per-story smoke (fix + re-smoke, never deferred-as-shipped without the user's explicit call).

**Why:** Epic 9.11–9.14. Every per-story smoke AND a CLEAN code-review approval passed, yet a posted announcement produced a proto-room the operator could not open or reply to — the gap lived BETWEEN "post an announcement" (9.11) and "browse/respond to rooms" (the earlier Epic-9 surface), invisible to both stories' AC-shaped tests. A real user hit it within minutes of free-form testing. The same lesson one scope down: the 9.11 `＋ open a room` defect (unreachable on a room-less board) passed dev+QA+CR green and was caught only by the per-story smoke. AC-shaped verification is necessary but structurally cannot see the seams; the integrated exploratory smoke is the gate that does. Pairs with Rule 12 (real-browser smoke) — this rule is about the SCOPE of the smoke (whole flow, free-form), Rule 12 about its FIDELITY (real browser).

## 15. A parity/mirror surface must be audited in BOTH directions against the mirrored capability's FULL op set

**Context:** Building a surface that gives one actor a capability another actor already has — an operator UI mirroring an agent, an alternate client mirroring the primary, an adapter mirroring a protocol. The explicit goal is parity with an existing actor's abilities.

**Rule:** Before scoping the surface, ENUMERATE the mirrored actor's full op set and audit that the new surface covers BOTH halves of every interaction: the INITIATE/produce verbs AND the RESPOND/consume verbs. A partial parity — can create but not read/act-on, can send but not receive, can announce but not answer — ships green against its own ACs and FEELS BROKEN to the user, because real use is a loop, not a one-way push. Do not scope only the "produce" side because it is the obvious/demo-able half. If a respond/consume verb is deferred, name it explicitly (a follow-up story / deferred-work item), never leave it as an unspoken hole.

**Why:** Epic 9. Stories 9.11–9.13 delivered the operator's INITIATE surface (announce_project / post_announcement / join_board / update_focus) — the produce half of parity. But the RESPOND half (open / read / reply-to-activate an announced proto-room — what an agent does via `list_announcements` + `reply`) was entirely missing: the operator could post an announcement but never see or answer one, and could never be the actor who activates a proto-room. That asymmetry WAS the user's "I posted an announcement but nothing appears." Story 9.14 closed it by mapping the respond half to the SAME existing `reply` op an agent uses. The parity epic scoped the easy/demo-able direction and silently dropped the other; a both-directions audit at scoping time would have caught it before any code.

## 16. A per-story smoke must cross the story's CONSUMER seam, not stop at "the produce step succeeded"

**Context:** The per-story smoke (Rule-12 gate) of a story that PRODUCES something a later step or sibling surface consumes — it creates a record, emits an event, or exposes an affordance that something else is meant to open/read/act on.

**Rule:** The smoke must exercise the story's output the way a CONSUMER would in the integrated app — after the produce step, OPEN / READ / ACT ON what was just created — not stop the moment the produce call returns success + a count/toast updates. "Post succeeded and the counter incremented" is not the same as "the thing I posted is now usable." Crossing the consumer seam in the per-story smoke surfaces seam gaps ONE STORY EARLY instead of deferring them to the end-of-epic integrated smoke (Rule 14) or to a user.

**Why:** Epic 9.11. The 9.11 per-story smoke proved "post an announcement succeeds" and stopped at the incremented `announcements (N)` count — green. Had it gone one step further and tried to OPEN the just-posted announcement, the proto-room navigability gap (no navigable row, no way to read/reply) would have surfaced immediately, inside 9.11, instead of surviving to the end-of-epic heavy smoke and a real user. The produce-side assertion was load-bearing but stopped at the seam; the consumer-side step is cheap and catches the class of "created but unusable" defects. The narrow version of Rule 14, applied at per-story scope.

## 17. A webview/iframe-client smoke must MOUNT the real bundle in the real host and exercise the live message round-trip + content render — a dispatch-direct probe and a DOM-shim test are necessary but NOT sufficient

**Context:** A story shipping a sandboxed embedded-client surface that loads its OWN script bundle inside a host-managed container and talks to the host over an async message channel — a VS Code `WebviewPanel`, a browser `<iframe>`, a Worker, an Electron `BrowserView`. The client mounts a UI framework (React, etc.) and fetches its data via `postMessage` request/response (not a direct function call).

**Rule:** The load-bearing smoke (and ideally an automated tier) MUST load the ACTUAL built bundle in the REAL host (e.g. `@vscode/test-electron`; a real browser via chrome-devtools-mcp) and drive the LIVE path end-to-end: the bundle mounts, issues a real `postMessage` request, the host's handler answers over the real channel, and the **rendered content actually appears** (assert on visible DOM text/state, not just "the panel opened"). Two cheaper tiers are explicitly INSUFFICIENT and must not be mistaken for this: (a) a DOM-shim test (jsdom/happy-dom) — it does NOT enforce CSP, does not run the host's sandbox, and may not run WASM/workers as the real host does; (b) a probe that calls the host's request-dispatch FUNCTION directly (`dispatchRequest(...)`) — it bypasses `acquireVsCodeApi()`↔`postMessage`↔the `window` 'message' listener AND the UI framework's mount lifecycle (e.g. React StrictMode's mount/unmount/remount). Sharpens Rule 12 (real browser) to "real BUNDLE mounted + real ROUND-TRIP + content RENDERED," and extends Rule 16 (cross the consumer seam) to the embedded-client transport seam.

**Why:** Epic 10. Three real defects shipped green through unit + DOM-shim + the `dispatchRequest`-direct `@vscode/test-electron` probes and a CLEAN code review, and were caught ONLY when a human/agent drove the actual extension in a real VS Code host (Rule-14 manual smoke): (1) the room webview hung on "opening room…" because React **StrictMode**'s simulated unmount disposed the postMessage bridge's `window` listener and it was never recreated (the fake-bridge unit tests inject the `Bridge` interface directly; the in-host probe called `dispatchRequest` directly — neither mounts the real bundle, so neither sees the StrictMode lifecycle); (2) every message body rendered EMPTY because the strict CSP blocked Shiki's WASM (`renderMarkdown` never resolved) — **happy-dom does not enforce CSP**, so no shim test could see it; (3) the produce/consume round-trip only worked once `createPostMessageBridge`↔host `createBridge` were exercised over a real channel, which no test did. The fix added a happy-dom test that mounts the real root under `<StrictMode>` with a mock `acquireVsCodeApi` wired to the real host bridge over a simulated channel (catches #1/#3), but #2 (CSP-blocks-WASM) is structurally real-host-only — so the real-host mount smoke is the load-bearing gate, not optional.

## 18. A substring-based forbid guard needs PRECISE-token matching when a legitimate longer token contains the forbidden substring — and adding such a token means updating EVERY guard that checks it

**Context:** A content-guard / drift-guard asserts a string does NOT contain a forbidden token via a naive substring check (`!s.includes('unsafe-eval')`, a `not.toContain('overlay')`, etc.), AND the surface legitimately gains a LONGER token that CONTAINS that substring (`'wasm-unsafe-eval'` ⊃ `unsafe-eval`; a class `overlay-none` ⊃ `overlay`). Especially when the same property is checked by MULTIPLE guards (unit fixtures + an in-host/integration probe + a runner assertion).

**Rule:** When a legitimate token is a superstring of a forbidden one, the guard MUST match the forbidden token PRECISELY (a word/token boundary or a negative lookbehind, e.g. `/(?<!wasm-)unsafe-eval/`, or split-on-whitespace exact-token compare), never a bare substring — and it should POSITIVELY PIN the legitimate token's presence so it cannot silently regress. Crucially: when you introduce such a token, grep for EVERY guard that asserts on that property and update ALL of them in the same change — unit guards, the in-host/real-runtime probe's assertion, and any runner-side check. A guard updated in one tier but not another produces a false-RED in the un-updated tier (or, worse, a false-GREEN hole).

**Why:** Epic 10 defect-fix #2. Adding `'wasm-unsafe-eval'` to the webview `script-src` (the narrow WASM token — NOT `unsafe-inline`/`unsafe-eval`) made the byte-shared Shiki markdown renderer work under the strict CSP. The dev updated the UNIT content-guards to precise-token matching (`/(?<!wasm-)unsafe-eval/` + a positive pin that `wasm-unsafe-eval` is present), and mutation-tested them. But the **in-host `@vscode/test-electron` probe** (`room-panel.in-host.ts`) still used `!html.includes('unsafe-eval')` AND an exact `^script-src 'nonce-…'$` regex — both correctly-failing on the now-legitimate token — so the full real-host probe suite went RED on a CORRECT CSP (a pure false-fail; the product was right + user-confirmed). One token, checked in four places; three were updated, one missed. Same class as the Rule-10/Epic-8 call-form blind spot (a guard that doesn't match every form/place the token appears).

## 19. A thin client mounting a byte-shared component INHERITS that component's runtime requirements — verify them against the new host's sandbox at integration

**Context:** A new thin client (Rule 13) mounts a byte-shared UI component/library that was built and proven in a DIFFERENT host (e.g. `ui-shared` proven in the web app), now embedded in a host with a tighter or simply different runtime sandbox — a VS Code webview CSP, an iframe `sandbox`, a Worker scope, a service worker, a stricter Electron context.

**Rule:** Before declaring the byte-shared mount done, ENUMERATE the shared component's RUNTIME dependencies — WASM compilation, network fetches, web workers, dynamic `import()`, inline styles/scripts, fonts, `eval` — and verify the NEW host's sandbox (CSP directives, `sandbox` attrs, allowed origins, bundle mode) ACCOMMODATES each, or the shared component will fail SILENTLY in the new host (often rendering empty rather than erroring loudly). Reusing a component byte-identically (the correct Rule-13 move) does NOT mean its host requirements are free — they travel with it. If the host genuinely must stay stricter than the component needs, that's a reconcile-explicitly decision (Rule 8): relax the host narrowly (the purpose-built token, not a blanket loosening), OR move the requirement out of the client (e.g. host-side pre-render), OR add a graceful-degradation path to the shared component — never leave it silently broken.

**Why:** Epic 10. The byte-shared `ui-shared` `MarkdownView` runs Shiki's oniguruma regex engine as **WebAssembly** (bundled). It works in `apps/web` (no strict CSP). Mounted unchanged in the VS Code room webview under the Story-10.5 strict CSP (`script-src 'nonce-…'`, no `wasm-unsafe-eval`), `WebAssembly.instantiate` was blocked → `renderMarkdown` never resolved → EVERY message body rendered empty, with no error surfaced to the user. The component was correctly byte-identical (Rule 13 held); the miss was not auditing its WASM requirement against the host CSP. Reconciled per Rule 8 by adding ONLY the narrow `'wasm-unsafe-eval'` token (NFR12 inert rendering preserved; no `unsafe-inline`/`unsafe-eval`). Extends Rule 13: a thin client inherits not just the shared component's CODE but its RUNTIME contract with the host.

## 20. A "gate is green" claim is unverified until INDEPENDENTLY re-run — and the gate is lint + typecheck + build + test + format, not just test

**Context:** A dev/QA stage's closing summary asserts the canonical gate is green (e.g. "lint 0 / typecheck 0 / test N passed / format clean"). The reviewer/lead is about to trust that claim to advance the pipeline (skip a re-run, approve, commit).

**Rule:** Treat a stage's "gate green" claim as a CLAIM TO RE-VERIFY, not a fact — the reviewer/lead (or the next stage) MUST independently re-run the FULL canonical gate and confirm every leg before trusting it. Crucially, the gate is ALL of `lint` + `typecheck` + `build` + `test` + `format --check`, not just the test count: a green test suite while `lint`/`prettier` are RED is a FALSE GREEN. Watch the recurring false-green classes specifically: a rest-sibling destructure-drop (`const { x: _drop, ...rest } = o`) that the project's ESLint config does NOT exempt (no `ignoreRestSiblings`/`varsIgnorePattern`) → `no-unused-vars` RED; an over-width or unformatted line → `prettier --check` RED; a test that passes under the Vitest src-alias but breaks `tsc` typecheck. The lead's per-story smoke re-running the gate is the binding backstop; never let a self-reported green substitute for it.

**Why:** Epic 11 Story 11.2. The dev's Dev Agent Record claimed "lint 0 / format clean", but the code-review stage re-ran the canonical ROOT gate and found it RED: two `no-unused-vars` errors (a `const { actor: _dropped, ...rest }` destructure-drop the repo's flat ESLint config does not honor) plus one over-width line failing `prettier --check`. The product logic was correct and the tests passed, so the test-count claim was true — but "the gate is green" was FALSE because lint+prettier were red. CR auto-resolved it inline (rewrote the drops to `{...e}; delete x.actor`, formatted) and only then was the gate genuinely green (1526/177). A pipeline that trusted the dev's "lint 0/format clean" verbatim would have committed a red-gate changeset. The defense is mechanical: the next stage re-runs the WHOLE gate, every leg, before trusting the claim — exactly what caught it here.

## 21. A doc/prose REWRITE must be encoding-verified out-of-band — a machine-TOKEN content-guard is blind to multibyte-glyph corruption (mojibake / BOM)

**Context:** An agent REWRITES (not just appends to) a human-or-machine-consumed document that contains non-ASCII characters — em-dashes (`—`), arrows (`→`), emoji (`👍`), box-drawing (`├`/`└`), smart quotes — especially when the rewrite round-trips the file through a shell/regex/encoding-lossy path. The doc may ALSO have a Rule-10 content-guard pinning its machine tokens.

**Rule:** After any prose rewrite of a file with non-ASCII content, VERIFY THE ENCODING OUT-OF-BAND before trusting it: no spurious BOM, no mojibake sequences (`—`→`â€"`, `👍`→`ðŸ‘`, `→`→`â†'`, box-drawing→`â”œ`), consistent UTF-8 + LF. Do NOT rely on the Rule-10 content-guard to catch this — that guard pins ASCII MACHINE TOKENS (tool names, error codes, bin names, the env var) which survive a mojibake round-trip BYTE-INTACT, so the guard stays GREEN while the surrounding human-facing prose is corrupted into garbage. A grep for the known mojibake lead-bytes (`\xc3\xa2`, `\xef\xbb\xbf` BOM) or a visual render is the actual check. If corruption is found, reverse it per-character (mojibake is a deterministic double-encode, fully recoverable) + strip the BOM + normalize to LF, then re-confirm the machine tokens are still byte-intact.

**Why:** Epic 11 Story 11.5. The README — the canonical OSS stand-up artifact an outside dev relies on — was rewritten from its placeholder state and shipped UTF-8-CORRUPTED: a spurious BOM plus 97 mojibake sequences (em-dash→`â€"`, 👍→`ðŸ‘`, arrow→`â†'`, box-drawing→`â”œ`), introduced via a double-encode round-trip during the rewrite. The AC6 Rule-10 content-guard was CORRECTLY green and non-vacuous — every ASCII machine token (`agentbbs`, `agentbbs-mcp-server`, `AGENTBBS_DB`, the 17-tool claim) survived byte-intact — but it is STRUCTURALLY blind to prose-glyph mojibake, so green told us nothing about the reader-facing text. The code review caught it out-of-band (a grep + render), reversed the encoding per-char (0 unrecoverable), stripped the BOM, normalized to LF, and reconfirmed every machine token + the sentinel block intact. A token-pinning content-guard (Rule 10) and prose-encoding integrity are ORTHOGONAL concerns: the guard protects what the machine reads, this rule protects what the human reads — both are required for an OSS-facing doc.
