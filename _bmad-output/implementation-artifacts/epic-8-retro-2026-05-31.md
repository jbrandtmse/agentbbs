## Challenges / Lessons

- **[PRIMARY] An agent-executed asset with safety-critical mechanics must make those mechanics an EXTRACTABLE, EXECUTABLE unit — prose the agent hand-implements each run cannot be tested and will eventually corrupt a consumer's files.** 8.4's kit writes files in a stranger's project; its idempotency / backup / never-touch-foreign properties are load-bearing. Shipping them as an inline `applyBlock`/`mergeMcpServer` helper the agent INVOKES (rather than "instructions for the agent to carefully edit files by hand") made them (a) DETERMINISTIC at install time and (b) directly TESTABLE — the safety test runs the kit's own extracted code. Had the kit only described the procedure in prose, the safety properties would be unverifiable and re-derived (possibly wrongly) on every run. → Rule 11.
- **When a smoke/test fails against a well-reviewed artifact, suspect the TEST's usage of the contract before the artifact.** The 8.4 lead smoke first went RED on idempotency — but the cause was the SMOKE passing the sentinel markers INSIDE `blockContent` when `applyBlock`'s JSDoc says "the content to place BETWEEN the markers (markers added by this fn)". The kit was correct; the smoke misused the contract. Reading the helper's documented signature resolved it in one pass. This is Rule 4 (verify against the source of truth — here the helper's own JSDoc) applied to a test-authoring mistake: a red bar is not automatically an artifact defect. (Recorded as a debugging-discipline note, already covered by Rule 4; no new rule.)
- **A content-guard can false-positive on its own author's prose, and that is the guard WORKING.** Twice (8.4 dev + 8.4 review) the kit's `no-phantom-tools` guard flagged backticked NON-tool tokens the author introduced (`` `curl` ``, the server name `` `agentbbs` ``, JSDoc action words `` `created` ``/`` `replaced` ``). Each was resolved by un-backticking the prose or allowlisting the genuinely-non-tool token — never by weakening the scan. The friction is the guard doing its job; the discipline is to keep the allowlist minimal and reword prose rather than broaden the escape hatch. (Folded into Rule 10's existing guidance — no new rule.)

## Rules to Codify (meta-rule step)

One general-pattern lesson rose to class-of-issues shape and is codified in `.claude/rules/project-rules.md` (the file had Rules 1–10, so this lands as **Rule 11**):

- **Rule 11 — When an agent-executed asset carries a SAFETY-CRITICAL DETERMINISTIC PROCEDURE (idempotent edits, backup-before-overwrite, never-touch-foreign, key-scoped merges), ship that procedure as an EXTRACTABLE, EXECUTABLE unit inside the asset and prove its properties by EXECUTING the asset's OWN extracted code against real fixtures — never by prose review or a test re-implementation.** Motivated by Epic 8 Story 8.4: the `install-agentbbs.md` kit writes files in a stranger's project; its idempotency / timestamped-backup / never-touch-foreign (incl. the project's `epic-cycle` kit) / `.mcp.json` key-scoping are load-bearing. The kit ships an inline `applyBlock`/`mergeMcpServer` Node helper, and the safety test EXTRACTS + IMPORTS + EXECUTES that exact helper against temp files (planted foreign assets survive byte-identical; re-runs are byte no-ops; changes back up first), mutation-tested non-vacuous (defeating the idempotency short-circuit → RED; dropping foreign servers → RED). This extends Rule 10 (which pins what an asset SAYS to the code) to what an asset DOES: a safety-critical procedure described only in prose is re-derived — possibly wrongly — on every agent run and cannot be regression-tested; making it an extractable executable makes it deterministic AND testable on the asset's own instrument.
