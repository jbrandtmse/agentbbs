## Challenges / Lessons

- **[PRIMARY] A story Source-fact asserting an existing repo symbol was WRONG and nearly mis-scoped a story (4.5 `HANDLE_NOT_FOUND`).** The lead-authored Story 4.5 claimed `HANDLE_NOT_FOUND` "already in the closed set at `errors.ts:29`" — but line 29 was `BOARD_NOT_FOUND`; the code did not exist. The dev grepped, found the claim false, and added `HANDLE_NOT_FOUND` additively (correct, non-breaking per the error-contract policy), surfacing it loudly. Root cause: this epic's stories were lead-authored directly (for context efficiency across the 23-story batch) rather than via the create-story skill's exhaustive artifact pass, so a "Source fact" was asserted from memory rather than verified against the repo. **No harm done** (the dev's verification caught it at zero cost), but it is a class-of-issue: a confidently-wrong source-fact about an existing symbol/signature/code can mis-scope a story. → **codified as Rule 10** (verify story-asserted internal repo facts before coding to them — the internal-symbol analogue of Rule 3's external-API verification).
- **Concurrency ACs are only genuinely proven by a cross-process race, and the dev stage twice tried to defer/skip it.** In 4.3 and 4.5 the dev argued a plain `append` (no `appendGuarded`) needed no race test beyond the sequential proof; QA overrode both times and the races caught real, otherwise-untested guarantees (the activator min-`seq` derivation and the benign double-join/double-add dedup under genuine contention — neither exercised by Epic 1's `concurrency.test.ts`, which only stresses `identity.seen`). → **codified as Rule 11** (a concurrency-claiming AC requires a genuine cross-process race; sequential coverage does not satisfy it).
- **A corrupted tool result nearly injected a phantom code change during the 4.5 code review.** The reviewer received a fabricated `Read` of `append.ts` showing code that does not exist, "found" a SQLite concurrency defect, and began applying an `.immediate()` fix — then caught it by checking `git show`/`git diff` ground-truth (the file was unchanged) and fully reversed it. The lead independently re-verified the working tree (`git diff HEAD -- append.ts connection.ts` empty) before committing. → **codified as Rule 12** (when a tool result contradicts committed/known state, verify against git ground-truth before acting). This protects every agent stage, not just review.
- **Tool/test-count drift in tracking docs.** Several stages reported slightly different running test counts (e.g. 476 vs 475) and a "11th vs 12th tool" off-by-one, each reconciled by the next reviewer. Harmless (the gate is the source of truth, not the prose count), but it cost reviewer cycles re-deriving the number. Minor; not rule-worthy — the cycle log's per-stage `tests_added` is the durable record.

## Rules to Codify (meta-rule step)

Three general-pattern lessons rose to class-of-bugs shape and are codified in `.claude/rules/project-rules.md` (the file had Rules 1–3, so these land as **Rules 4, 5, 6**):

- **Rule 4 — Verify story-asserted internal repo facts (existing symbols, error codes, signatures, file:line) against the repo before coding to them.** Motivated by Story 4.5's wrong `HANDLE_NOT_FOUND` "already exists" source-fact. The internal-codebase analogue of Rule 3 (external-API verification). A confidently-wrong source-fact mis-scopes a story; the dev/reviewer must treat story Source-facts as claims to confirm, not gospel.
- **Rule 5 — A concurrency-claiming AC requires a genuine cross-process (forked) race test; sequential coverage does not satisfy it.** Motivated by the dev deferring the 4.3/4.5 races that QA then proved caught real, otherwise-untested guarantees (activator min-`seq`; benign double-join/add dedup). "Plain append, nothing to stress" is not a sufficient reason to skip the race.
- **Rule 6 — When a tool result contradicts committed/known state, verify against git ground-truth before acting on it.** Motivated by the corrupted-tool-result phantom-defect episode in the 4.5 review (a fabricated file read nearly produced a spurious code change). Protects every agent stage.

(Note: these `project-rules.md` numbers are distinct from the `_bmad/custom/skill-rules.md` Rule 1/3/5/6/8 referenced by the dev/review STAGES — two separate rule files.)
