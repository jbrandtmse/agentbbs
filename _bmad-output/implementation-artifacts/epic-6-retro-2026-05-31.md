## What Went Well

- **The carried perf items (3.0-b, 4.6-a) were deferred to their NAMED CONSUMER and resolved THERE with measured evidence — exactly as the deferred-work process intends.** They were flagged at the Story-3.0 / Story-4.6 code reviews, explicitly pointed at "Story 6.1 (the `check` hot-path consumer)", carried untouched for 2–3 epics (no premature optimization), then 6.1 MEASURED the real per-call fold cost and applied a contained ~8× optimization, closing both with evidence. Neither was optimized before the consumer existed, and neither was carried indefinitely without measurement. → **codified as Rule 9** (defer a perf/cost concern to its named-consumer story for measurement; close it there with evidence or a contained fix — not prematurely, not indefinitely).
- **The first MUTABLE store landed without breaking the append-only spine.** `check` needs a stored per-identity cursor (architecture line 253 — "per-identity stored position … legitimate bookkeeping"). The lead chose a SEPARATE `cursors(handle PK, seq)` table with an UPSERT, explicitly NOT the `events` table — and the append-invariant lint guard (which matches a literal `UPDATE events`/`DELETE FROM events`) correctly did NOT fire on `DO UPDATE SET seq`. The reviewer confirmed empirically (lint green) and structurally (zero `events` mutations). The one architecture-sanctioned exception was introduced cleanly, with the boundary explicit.
- **Flood-prevention by per-scope FLOORS (not cursor-init) proved correct.** 4.6's per-room floor + 6.1's new per-board floor compose with the global cursor as `seq > max(cursor, joinFloor)` — so a late joiner is never flooded with back-history, AND the cursor purely tracks "since last check" (no single-cursor skip problem). The 4.6 design decision paid off exactly as forward-declared in its barrel comment.
- **`check` advancing to `maxReturned` (not `maxSeq`) made the concurrency AC trivially correct,** and QA proved it under a genuine 8-process forked race (no in-scope message skipped, cursor monotonic, UPSERT + presence consistent under real WAL serialization — Rule 5 applied).
- **The lead-side no-code Story 6.0 was proportionate.** Every Epic-5 carried item routed elsewhere (perf → 6.1, contract → Epic 7, no-trigger defers), so 6.0 had no actionable cleanup; handling it as a lead-side triage record (no dev/QA/CR/smoke pipeline) avoided spinning a no-op pipeline while still performing + recording the gate triage.

## Challenges / Lessons

- **[PRIMARY] The carried perf items had no home until their consumer existed — the deferred-work "→ named consumer" pointer was load-bearing.** 3.0-b/4.6-a could not be sensibly measured or optimized at their origin epics (no hot-path consumer yet); the value was entirely in (a) NOT optimizing prematurely and (b) ensuring the named consumer (6.1) actually measured them rather than carrying them forever. → Rule 9 (above).
- **The MCP tool COUNT drifted into a user-facing doc (6.2 said "12 tools"; `server.ts` registers 17).** This is the long-tracked `E3-tool-names`/`4.5-tool-label` item — the tool surface has never been contract-pinned, and the original architecture's "12 tools" estimate is now wrong (Epics 4–6 added 8). The 6.2 reviewer fixed the doc to count-agnostic phrasing, but the underlying drift will keep recurring until **Epic 7's `mcp-tool-contract.md`** ratifies the actual ~17-tool surface + names + envelopes. Not rule-worthy (it is a tracked deferral with a named destination), but it is now appearing in open-source-facing docs (NFR8), so Epic 7 should treat the contract as DUE, not optional.
- **`check` reads `eventsSince(0)` (the full stream) for SCOPE even though the RESPONSE is bounded.** The "bounded" guarantee is about the response (delta-only); the query still folds the full history to know the actor's memberships/participations/floors. 6.1 measured this acceptable at V1 (the ~8× optimization + the 6.2 query-cost smoke under 2000ms at 400 events), but it is an O(total-events) scope fold per dial-in — the documented V1 cost, with the data-access seam (NFR2) the place a scoped/indexed read would land if a networked backend ever needs it. Honestly surfaced (Rule 5), not papered over; no tripwire at V1 scale.

## Rules to Codify (meta-rule step)

One general-pattern lesson rose to class-of-issues shape and is codified in `.claude/rules/project-rules.md` (the file had Rules 1–8, so this lands as **Rule 9**):

- **Rule 9 — Defer a performance/cost concern to its NAMED-CONSUMER story for measurement; close it there with measured evidence (or a contained fix) — not prematurely, not indefinitely.** Motivated by 3.0-b + 4.6-a: flagged at code review, pointed at "Story 6.1 (the `check` hot-path consumer)", carried untouched for 2–3 epics (no premature optimization), then MEASURED at 6.1 (real timing) and closed with a contained ~8× optimization. Prevents both the class of premature optimization (tuning before the consumer/hot-path exists, often the wrong tuning) AND the class of silent perf debt (a perf item carried forever without ever being measured). The deferred-work entry MUST name the consumer that will measure it.

The other Epic-6 lessons are tracked, not codified: the tool-count drift is a known deferral with a named destination (Epic 7), and the `cursors` mutable-store carve-out is a one-off architecture decision (there is one such store), each recorded here + in `deferred-work.md` rather than rising to a recurring class-of-bugs rule.
