## Deferred from: code review of story 1.4 (2026-05-31)

- **Story 1.4 · LOW · `runWithRetry` has no inter-attempt backoff for immediately-surfaced busy errors. — RESOLVED (validated by Story 1.7, 2026-05-31).**
  - **Resolution:** Story 1.7 (the named multi-process concurrency consumer that stresses this path) proved the busy_timeout+retry model resolves real cross-process contention with margin: N=6 writers × M=100 = 600 appends produced exactly 600 unique, strictly-monotonic `seq` rows with no lost writes, and `busyErrors` stayed **0** across all writers. The contention probe confirmed the busy/retry path is genuinely traversed (per-writer `maxAppendMs` 184–448 ms against writer 0's 150 ms held lock) yet still never surfaced a premature `StoreBusyError`; the test ran 22× consecutively, all green. The zero-backoff retry was therefore never the bottleneck under genuine load — production connections open with `busy_timeout=5000`, which spaces contended attempts inside each `fn()`. The speculative inter-attempt backoff is not needed; close as resolved-by-evidence. [Source: 1-7-multi-process-concurrency-verification.md — Completion Notes / contention probe.]
  - **Summary:** `runWithRetry` (`packages/data-access/src/sqlite/connection.ts`) retries a busy `fn()` back-to-back with zero delay between whole-call attempts. The documented concurrency model relies on better-sqlite3's per-call `busy_timeout=5000ms` to block-and-wait *inside* each `fn()` before it throws, so in real contention the bounded attempts are naturally spaced (~`busy_timeout × attempts` worst case). For busy errors that SQLite surfaces *immediately* without waiting (e.g. a `SQLITE_BUSY_SNAPSHOT` WAL write-write collision, or any connection that has set `busy_timeout=0`), all `MAX_WRITE_ATTEMPTS` (3) fire within microseconds — the retry provides little practical benefit in that narrow case. The behavior is correctly BOUNDED (no busy-spin: capped at `attempts`, then a typed `StoreBusyError`), and matches NFR3/AR4 as worded ("WAL + busy_timeout + bounded retry" — no jittered-backoff requirement). Not a blocker.
  - **Rationale:** Production connections all open with `busy_timeout=5000` (verified in `openDatabase`), so genuine cross-process contention DOES space the attempts; the zero-gap path is only reachable with the `busy_timeout=0` test-harness condition or the residual instant-`SQLITE_BUSY_SNAPSHOT` case. Adding backoff now would be speculative tuning ahead of real evidence and outside this story's "connection plumbing only" scope.
  - **Suggested resolution:** Validate retry behavior under genuine sustained N×M contention in **Story 1.7** (the multi-process concurrency proof, which is the named consumer that stresses this path). If 1.7 surfaces lost writes or premature `StoreBusyError`s under real load, add a small bounded backoff (e.g. a few ms, optionally jittered) between whole-call attempts in `runWithRetry`. Until then, leave as-is.

## Deferred from: code review of story 1.6 (2026-05-30)

- **Story 1.6 · LOW · `wireToPayload` does not validate the payload shape of a known-type-but-malformed row. — OPEN (carried forward; Story 2.0 triage 2026-05-31).**
  - **Summary:** `rowToEvent` (`packages/data-access/src/mapping.ts`) hardens the `type` column via `asEventType` (throws loudly on an unknown/foreign type). The payload conversion in `wireToPayload`, however, reads each expected key positionally and coerces with `String(...)`/`Number(...)`. A row whose `type` is a *valid* vocabulary value but whose stored JSON payload is missing or malformed (e.g. external DB tampering, or a future producer bug) would map silently: a missing string key becomes `"undefined"` and a missing `message_seq` becomes `NaN`, rather than failing at the seam. On the happy path this never occurs — payloads are written by `payloadToWire` in the same module and stored verbatim by SQLite, and the all-10-type real-runtime round-trip proves the producer↔consumer contract is exact. The gap is reachable only by a foreign/corrupt row with a known type.
  - **Rationale:** The read direction's contract for this story is the write→read round-trip (fully proven). Defence against externally-corrupted payloads is a validation/hardening concern, not a mapping-fidelity concern, and adding per-field schema validation (e.g. a Zod parse at the seam) is out of scope for the read-query/mapping story — it would also need a decision on the failure mode (throw vs. skip-and-log) that belongs with the projection/validation consumer. Type-column hardening (the loud-failure case most likely to leak an *untyped* event into core) is already in place.
  - **Suggested resolution:** When a payload-validation story lands (or when the first `core` projection in Epic 2+ folds these events and needs corruption-tolerance), parse each read-back payload against its `EventPayloadMap` shape at the `mapping.ts` seam (Zod v4 is already the project's boundary validator) and throw a typed seam error on a malformed-but-known-type row, mirroring `asEventType`'s loud-failure stance. Until then, the type-column guard plus the round-trip contract are sufficient for Epic 1.

## Deferred from: code review of story 2.4 (2026-05-31)

- **Story 2.4 (process; spans Epic 2) · LOW · Cross-package tests need a `core` build before they see newly-added `core` exports (monorepo build-ordering papercut). — OPEN.**
  - **Summary:** `@agentbbs/mcp-server` tests import `@agentbbs/core` through its package `exports`, which resolve to the BUILT `core/dist/` — there is no `src` alias in the Vitest config, so cross-package specifiers are NOT served from TS source. When a story adds a new `core` export (Story 2.4 added `updateFocus` + `NO_IDENTITY`), the mcp-server integration/boundary tests do not see it until `core` is rebuilt: the tool delegate reads `updateFocus === undefined` → throws `TypeError` → mapped to `INTERNAL_ERROR`, producing a confusing red that looks like a logic bug but is purely staleness. Story 2.4's Debug Log documents hitting and diagnosing exactly this; the same class of "stale-dist `INTERNAL_ERROR`" was called out in the 2.4 review stage directive and has now surfaced across multiple Epic 2 stories that add core exports consumed by mcp-server. Intra-package (core-only) unit tests are unaffected because Vitest transforms intra-package source directly. Current mitigation is purely procedural: run `pnpm run build` before the full suite.
  - **Rationale:** Not a correctness defect — the production code and the tests are right; it is a developer-experience / gate-reliability papercut whose blast radius is "a dev or reviewer who runs `pnpm test` without a prior build gets a misleading `INTERNAL_ERROR`." It recurs every time a cross-package export is added, so it is a class-of-issue, not a one-off. Fixing it is a config/process change outside any single story's scope (and the 2.4 review directive explicitly said NOT to fix it in-story), so it is logged here for the Epic 2 retrospective to pick up.
  - **Suggested resolution (pick one; for the Epic 2 retro to decide):** (a) Add a Vitest `resolve.alias` mapping `@agentbbs/core` (and the other workspace packages) to their `src/index.ts` so cross-package tests run against live TS source and never need a prior build — simplest dev-experience win, but verify it does not mask a real `exports`/`dist` packaging problem (consider keeping ONE build-mode integration test that exercises the real `dist`); OR (b) add a root `pretest` script (`"pretest": "pnpm -r build"` or a scoped `pnpm --filter @agentbbs/core build`) so `pnpm test` always refreshes `dist` first — costs a build on every test run but keeps tests honest against the shipped artifact; OR (c) document the build-first requirement prominently (a `test` script banner / CONTRIBUTING note) if the team prefers to keep tests against `dist` with no aliasing. Whichever is chosen, capture it as an Epic 2 retro action so Epics 3–6 (which add many more core exports consumed by mcp-server) do not keep re-hitting it.
