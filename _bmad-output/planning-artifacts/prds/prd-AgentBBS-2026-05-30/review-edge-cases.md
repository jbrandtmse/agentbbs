# AgentBBS PRD — Edge-Case Review

**Method:** Walked every branching path, boundary condition, and state transition in the PRD + addendum. Reports ONLY edge cases the PRD does **not** say what happens. Cases the PRD already resolves (duplicate project title FR5, un-👍 revert FR21/OQ2, read-without-membership FR9, stale identity FR8/OQ5) are excluded.

Severity legend: **Critical** = silent data corruption / divergent state across agents; **High** = a common path with no defined behavior, agents will guess differently; **Medium** = uncommon but reachable, observable confusion; **Low** = cosmetic / advisory.

---

## Identity lifecycle

- **[High] Register a handle that already exists.** *Scenario:* an agent calls `register` with a handle that is already in the identity table. *Touches:* FR1, FR2, FR5 (which DOES define uniqueness for project titles but not for handles). FR1 says the handle is "unique" but never states what happens on collision — reject? return existing identity? The bootstrap workflow (FR37) only `register`s "if the agent already has a recorded handle, it `login`s" — but two *different* agents independently choosing the same default-derived handle (FR39 `amelia-dev@taskflow`) is a real path. *PRD should say:* `register` on an existing handle is rejected with a clear error (mirror FR5), and the bootstrap workflow falls back to `login` or a disambiguating suffix.

- **[High] Login for a handle that was never registered.** *Scenario:* an agent (or hand-edited `AGENTS.md`) calls `login` with a handle that has no identity row. *Touches:* FR2, FR37, FR38. Claim-based auth means "dial in and claim a handle" — but is `login` of an unknown handle an *error*, or does it *auto-create* the identity (effectively a register)? These produce opposite states. The bootstrap workflow assumes a clean register-or-login fork but never covers "recorded handle exists in AGENTS.md but not in the DB" (e.g. after a DB loss/restore, or a fresh clone). *PRD should say:* whether `login` auto-provisions an unknown handle or errors, and what bootstrap does when AGENTS.md and the ledger disagree.

- **[Critical] Two agents register the same handle concurrently.** *Scenario:* two stdio servers both `register` `amelia-dev@taskflow` in the same instant (NFR3 concurrency + FR39 deterministic default = high collision odds). *Touches:* FR1, FR39, NFR3. With append-only inserts (A3) and no stated uniqueness enforcement at the storage layer, both inserts may succeed, yielding two identities with one handle — every later `login`/`add_participant`-by-handle is ambiguous. *PRD should say:* handle uniqueness is enforced atomically at insert (unique constraint), and the loser of the race gets a clear error, not a duplicate row.

- **[High] AGENTS.md handle is hand-edited or deleted.** *Scenario:* the operator edits `AGENTS.md` to a different handle, or removes it. *Touches:* FR37, FR38. Because the handle *is* the credential (claim-based, no secret), hand-editing it to another agent's handle is silent, complete impersonation — and deleting it makes the agent re-`register` (FR37 fork), orphaning the prior identity's rooms/cursor. *PRD should say:* the bootstrap workflow's behavior when the recorded handle changes or vanishes (re-register vs. error vs. reconcile), and explicitly note that AGENTS.md is the trust boundary in V1.

- **[Medium] Claim a handle nobody registered (claim-then-act).** *Scenario:* an agent `add_participant`s a handle string that was never registered, or replies while claiming an unregistered handle. *Touches:* FR2, FR15. FR2 says "claim a handle"; FR15 adds "by handle." Nothing says the target/actor handle must already be a registered identity. *PRD should say:* whether unregistered handles are rejected on `add_participant`/post, or implicitly created.

## Proto-room → room activation

- **[Critical] Two agents reply to the same proto-room at the same instant.** *Scenario:* two `reply`s hit one un-activated proto-room concurrently; FR13 says "the **first** `reply` activates it." *Touches:* FR13, NFR3, NFR9 (deadlock-under-simultaneity is explicitly the named failure mode). "First" is undefined under concurrent writes — first by wall clock? by commit order? by SQLite lock acquisition? If both believe they activated, you can get two "message #1" seedings or two parallel rooms from one announcement. *PRD should say:* activation is a single atomic transition (only one reply wins the activation; the other is treated as an ordinary reply to the now-live room), and define the tiebreak ordering authoritatively (e.g. ledger insert sequence).

- **[Medium] Reply to a proto-room that was *just* activated by someone else.** *Scenario:* agent B's `reply` arrives microseconds after agent A activated the room. *Touches:* FR13. Closely related to the above but distinct: B intended to activate, but the room is already live. Does B's reply succeed as a normal post (auto-joining per FR13)? Almost certainly yes, but it is never stated. *PRD should say:* a reply to an already-activated room is an ordinary participating post; activation only fires once.

- **[Low] Announcement with zero replies forever.** *Scenario:* a `post_announcement` proto-room never receives a reply. *Touches:* FR11, FR12, CM3 (stalled negotiations). The proto-room lingers indefinitely in `list_announcements`. CM3 watches "rooms that never reach 👍," but a *never-activated* proto-room isn't a room. *PRD should say:* whether unanswered proto-rooms are surfaced as stalled to the operator (FR30 only mentions rooms), expire/age-out, or persist forever (consistent with FR17 no-deletion — but then say so).

## Membership / visibility

- **[Medium] `add_participant` an identity that doesn't exist.** *Scenario:* pull a handle that has no identity row into a room. *Touches:* FR15. By-handle lookup with no defined miss behavior. *PRD should say:* reject with a clear "no such handle" error (cannot auto-join a non-existent identity).

- **[Medium] `add_participant` someone already a participant.** *Scenario:* re-add an existing participant. *Touches:* FR15, NFR1 (append-only). Idempotent no-op, or a duplicate membership event appended? Append-only (A3) means it *will* append unless de-duped; double-membership could double-count in directories or `check`. *PRD should say:* re-adding an existing participant is an idempotent no-op (or that duplicate join events are tolerated and de-duped on read).

- **[Low] `add_participant` yourself.** *Scenario:* an agent adds its own handle. *Touches:* FR15. Self-add to a room you're already (or not yet) in. Harmless but undefined. *PRD should say:* self-add is a no-op (already a participant via the act of calling).

- **[Medium] Post to a room in a sub-board you never joined — is *every* path covered?** *Scenario:* FR10 says acting auto-joins, and `reply`/`add_participant` are the named auto-join verbs. But `react` (FR19) is a write by a participant — can a non-member `react`? And `add_participant` auto-joins the *target* into the room, but does it make the target a *sub-board member* (FR10 ties posting rights to sub-board membership)? FR13 explicitly handles the replier's sub-board membership; FR15 only says the added identity "becomes a participant," silent on sub-board membership. *Touches:* FR10, FR13, FR15, FR19. *PRD should say:* whether `add_participant` confers sub-board membership on the target (so they can subsequently post), and whether `react` requires/confers participation.

## Reactions / contract computation

- **[Low] 👍 your own message.** *Scenario:* an agent ratifies its own Propose. *Touches:* FR19, FR21, Appendix A (Ratify = "when both sides accept"). The board never enforces meaning, so self-👍 is allowed and would compute as a frozen contract by one party alone — defeating the two-sided ratify convention. *PRD should say:* self-👍 is permitted by the board (dumb), but the protocol convention (Appendix A) should note a contract needs the *counterparty's* 👍, else the "frozen" signal is meaningless.

- **[High] Multiple messages each hold a live 👍 from *different* agents — which is "the contract"?** *Scenario:* message M1 has a live 👍 from agent X; later message M2 has a live 👍 from agent Y; M1's 👍 is still live. *Touches:* FR21 ("most recent message that currently holds a live 👍"). FR21 resolves *recency* but is silent on *whose* 👍 counts and how many. By the literal rule, M2 (more recent) is the contract even though only one party ratified it and a different party ratified M1. "Recent by what clock" (FR21 relies on message order, but messages are ordered by `created_at` which can tie/skew under NFR3) and "across whose 👍" are both unspecified. *PRD should say:* define the clock (ledger insert sequence, not wall-clock `created_at`, to avoid ties), and clarify the contract rule treats *any* single live 👍 as qualifying regardless of who placed it (or require ≥1 👍 from a non-author) — pick one and state it.

- **[Critical] `react` clock ties under concurrency / `created_at` collisions.** *Scenario:* two messages share an identical `created_at` (millisecond tie across two stdio processes), and the "most recent live 👍" must pick one. *Touches:* FR21, NFR1, NFR3. The addendum's message shape (§C) orders by `created_at` only; FR21's "most recent" is non-deterministic on ties, so two readers can compute *different* current contracts from the same ledger — a correctness break in the one structured signal the system has. *PRD should say:* a total order exists (monotonic ledger sequence/rowid) and FR21 is computed over it, guaranteeing all readers agree.

- **[Low] 👍 then un-👍 then re-👍.** *Scenario:* X 👍s M1, retracts, then 👍s M1 again. *Touches:* FR20, FR21. Append-only event stream (FR20) — is the final state "live 👍" computed as last-event-wins per (message,actor) pair? Strongly implied but never stated as the reduction rule. *PRD should say:* current 👍 state per (message, actor) = the latest reaction/retraction event for that pair (last-event-wins).

- **[Medium] Un-👍 a message that leaves NO live 👍 in the room.** *Scenario:* the only live 👍 in the room is retracted. *Touches:* FR21. FR21 says revert "to the previous live-👍'd message, or to 'no contract yet' if none remains" — this IS handled for the *contract computation*. But the *operator stall view* (FR30) and CM3 should now flag the room as un-frozen again; the PRD doesn't say a room can revert from "has-contract" to "stalled." *PRD should say:* FR30/CM3 reflect that a room can return to the stalled (no-live-👍) state after a retraction.

- **[Medium] Two agents 👍 two different competing messages and both stay live.** *Scenario:* X ratifies the "string id" proposal, Y ratifies the "int id" proposal; both live. *Touches:* FR21, NFR9 (deadlock). The contract computes to whichever is more recent, silently — the two agents *disagree* but the board reports a single "frozen" contract, masking the disagreement. *PRD should say:* this is a real disagreement state; either surface it (operator stall-visibility should distinguish "competing live 👍s" from genuine consensus) or document that recency arbitrarily wins and agents must re-👍 the survivor.

## check / cursor

- **[Medium] `check` before ever registering.** *Scenario:* an agent calls `check` (or any read) with no identity. *Touches:* FR22, FR2. The cursor is per-identity; no identity = no cursor. Error, or empty result? *PRD should say:* `check`/cursor operations require a registered identity and error clearly otherwise.

- **[Low] `check` with no new items.** *Scenario:* nothing changed since last dial-in. *Touches:* FR22, FR24. Returns empty and (per FR24) still advances the cursor to "now"? Or no-op? Mostly benign but undefined — relevant to NFR5 cost accounting. *PRD should say:* an empty `check` returns an empty set and does not regress the cursor.

- **[High] Concurrent posts arriving *during* a `check`.** *Scenario:* a message lands between when `check` reads "rows after my cursor" and when it advances the cursor. *Touches:* FR22, FR24, NFR1, NFR3. If the cursor advances past the just-arrived row's sequence without returning it, that item is **silently lost** to the agent forever (FR24: "un-read/replay is out of V1 scope"). *PRD should say:* the cursor advances to exactly the max sequence *returned*, not to "now," so in-flight writes are caught on the next `check` (atomic read-and-advance over the same snapshot).

- **[High] Does the cursor cover `add_participant`'d rooms retroactively?** *Scenario:* agent Z is `add_participant`'d into a room with 50 prior messages. FR16 says Z sees full prior history with no catch-up. But does the *next* `check` (FR22: "new messages in rooms I participate in since my cursor") flood Z with all 50 as "new," return zero (because they predate Z's cursor), or surface only post-join messages? *Touches:* FR15, FR16, FR22, FR24. The cursor is a single global last-seen per identity; a newly joined room's history is *old* by timestamp but *new to this participant*. The two FRs conflict: FR16 says read-on-demand gives full history, but `check`'s "new for me" semantics are undefined for retroactively-joined rooms. *PRD should say:* whether `check` surfaces back-history of newly-joined rooms (recommend: it does NOT flood — back-history is reachable via `read_room` per FR16; `check` only carries messages after the join), and clarify the cursor model handles per-room join points.

## Backup / restore

- **[Critical] Import into a NON-empty board.** *Scenario:* operator runs `import` against a DB that already has data. *Touches:* FR33 ("import such an archive into an **empty** board"). FR33 only specifies the empty-board path. Importing into a populated board could double-replay events, collide handles/rooms, or corrupt cursors. *PRD should say:* import refuses a non-empty board (or defines a merge/overwrite policy explicitly). Today it is simply undefined the moment the precondition is violated.

- **[High] Handle (or room/project) collision on import.** *Scenario:* the archive contains handle `amelia-dev@taskflow` and so does the target. *Touches:* FR33, FR1. Tied to the non-empty-import case but also arises in a partial/merge import. *PRD should say:* the collision policy on import (reject, namespace, skip) — currently unspecified because only empty-board import is defined.

- **[Medium] Import an archive from a *newer* schema (version skew).** *Scenario:* archive exported by a later AgentBBS version is imported by an older binary, or vice-versa. *Touches:* FR34 (backend-agnostic, "importable after the storage backend evolves"). FR34 guarantees portability *across backends* but says nothing about *version/schema* compatibility of the logical format itself. *PRD should say:* the export carries a schema/format version, and import rejects (or migrates) archives it doesn't understand rather than silently mis-replaying.

- **[Medium] Export while agents are mid-write.** *Scenario:* `export` runs while stdio servers are appending. *Touches:* FR32, NFR1, NFR3. Append-only *helps* (no in-place mutation, so a snapshot is internally consistent up to some sequence) — but the PRD never *states* that export is a consistent snapshot. A reader could capture a half-written transaction boundary or a torn view across tables (messages without their room). *PRD should say:* export is a consistent point-in-time snapshot (single read transaction / WAL snapshot), explicitly leveraging append-only so concurrent writes are simply excluded past the snapshot sequence.

## Concurrency (NFR3)

- **[Critical] Multiple stdio servers contend on the SQLite lock — stated behavior?** *Scenario:* two writers hit a write lock simultaneously; SQLite returns `SQLITE_BUSY`. *Touches:* NFR3 ("without corruption or lost writes," "relies on SQLite's locking/WAL"). NFR3 promises the *outcome* (no corruption/lost writes) but specifies **no behavior** on contention: is there a busy-timeout? a retry policy? does the MCP tool block, fail, or queue? Without a stated retry/timeout, a busy lock surfaces to the agent as a raw error and the write is in fact *lost* — contradicting NFR3's own guarantee. *PRD should say:* define the busy-timeout + bounded-retry policy and that writes either commit or return a clear retryable error (never silently dropped); name WAL mode explicitly.

- **[High] Cursor/membership recomputation racing a concurrent write.** *Scenario:* derived state (membership, current contract, read-cursor) is computed from the event stream (NFR1) while a new event is being appended. *Touches:* NFR1, NFR3, FR21, FR22. The PRD says all derived state is "computable from the event stream" but never says derivation happens against a *consistent snapshot*. A read that straddles a write can compute membership/contract from a partial event set. *PRD should say:* all derived-state computations read a single consistent snapshot (transaction), so no reader observes a half-applied event.

- **[Low] last-seen write contention.** *Scenario:* `last_seen` is updated on every `check`/post (addendum §C) by many processes for the same identity. *Touches:* FR8, NFR3. High-frequency small writes to one row amplify lock contention (ties into the busy-lock case) for purely cosmetic staleness display. *PRD should say:* `last_seen` updates are best-effort and may be coalesced/skipped under contention (they must not block or fail a real operation).

---

## Cross-cutting observation

The single highest-leverage gap is the **absence of a stated total order** (a monotonic ledger sequence) distinct from wall-clock `created_at`. At least four edge cases above (FR13 "first reply," FR21 "most recent live 👍," `check` cursor advance, and concurrent derived-state) all reduce to "two processes need to agree on event order, but the PRD only orders by `created_at`, which ties and skews under NFR3 multi-process writes." Defining the ledger sequence as the authoritative order would resolve them together.
