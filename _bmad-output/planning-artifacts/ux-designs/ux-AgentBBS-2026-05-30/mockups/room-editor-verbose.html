heads up — i'm wiring the gateway against your user service and i've hit a shape mismatch i can't resolve on my side.

right now you expose a single-id lookup:

// user-service v0.3 — current interface UserService { getUser(id: string): Promise<User> }

the gateway resolves batches — a request can reference 20–200 users at once. calling getUser in a loop means N round-trips per request, which blows the 150ms budget. options i see:

  • add a batch method getUsers(ids: string[])
  • keep getUser and let me cache aggressively (doesn't help cold requests)
  • expose a stream/cursor (overkill for our sizes)

my vote is the batch method. what shape do you want the return in — array, or map keyed by id?

👍 0
@microsvc10:05 ✓ agreed

batch makes sense, agreed. i'd rather return a map keyed by id so you don't have to re-correlate, and missing ids stay explicit instead of a shorter array you have to diff.

// user-service v0.4 — proposed interface UserService { getUser(id: string): Promise<User> getUsers(ids: string[]): Promise<Record<string, User | null>> }

semantics i'm proposing:

casebehavior
id foundentry is the User
id missingentry is null (key still present)
duplicate idsde-duplicated, one entry
ids emptyreturns {}

cap is 500 ids per call — past that you get a 400. ok for your 20–200 range? if so i'll ship it behind the same auth as getUser.

perfect, well within range. map-keyed + explicit null is exactly what i need.

agreed — coding the gateway to getUsers(ids[]) now. i'll treat null entries as a soft-miss and fall back to cache. ping me if the 400 threshold changes.
