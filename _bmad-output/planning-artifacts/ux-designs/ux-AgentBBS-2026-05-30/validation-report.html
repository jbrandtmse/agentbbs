AgentBBS — UX Design Validation Report

_bmad-output/planning-artifacts/ux-designs/ux-AgentBBS-2026-05-30/ (DESIGN.md + EXPERIENCE.md)

A genuinely strong, source-extraction-ready spine pair: tokens are complete and every {path.to.token} reference resolves, the per-surface (web hex vs --vscode-* inheritance) model is committed cleanly, and the named-protagonist flow carries both Mode A and Mode B with shared climax and an escalation/failure path. The one real gap is component coverage parity — seven components carry visual specs (DESIGN frontmatter + body) but no behavioral row in EXPERIENCE.md, and one (Breadcrumb / joined row) carries behavior with no DESIGN frontmatter token — so a consumer building those components source-extracts a half-contract. Secondary: the spines-win-on-conflict guard is scoped to one mock only, leaving a superseded 3-direction comparison file (with two rejected palettes) extractable without warning.

Two additional reviewers ran alongside the rubric, and both sharpen rather than overturn that verdict. The cross-spine + PRD fidelity review confirms PRD fidelity is strong: every load-bearing reversal — FR30 no-stall-detection, FR21 computed-agreement, FR31 join-to-post, NFR12 inert rendering, OQ4 multi-surface — is honored on both surfaces with no contract-level contradiction, and the residual defects are the same component-name/coverage drift the rubric found, plus light-mode -light token gaps on two functional-color states. The VS Code platform-fit reviewer surfaces the one structural decision the spine never names: native TreeView vs. custom WebviewView for the sidebar — the tree's wish-list (2px accent left rail, literal •/° glyphs, multi-digit count pills) assumes more control than a native TreeView grants and collides with the hard 2-character FileDecoration.badge cap; that fork, plus right-sizing the decoration vocabulary and a few theme-token corrections, is where extension-surface parity claims will break first if left implicit.

VS Code platform-fit

review-vscode-fit.md

"This is an unusually platform-literate design: the multi-surface model (web carries hex brand; VS Code inherits --vscode-*) is exactly right, every named theme token is real and well-chosen, and 'rooms as editor tabs' + 'tree in the sidebar' are the correct idioms. The one structural fork the spine never names is native TreeView vs. custom WebviewView for the sidebar — and the design's tree styling wish-list (2px accent left rail, a literal •/° glyph set, multi-digit count pills, custom row fills) quietly assumes more control than a native TreeView grants, while the count badge collides with VS Code's hard 2-character FileDecoration.badge limit. Resolve the TreeView-vs-Webview decision and right-size the decoration vocabulary and this design is faithfully buildable; leave it implicit and the sidebar is where parity claims will break first." Recommendation: native TreeView (treat the rail + pill as documented web↔VS Code deltas); one WebviewPanel per room with an explicit retention policy; three theme-token corrections; explicit CSP for inert rendering.

high

Sidebar tree specified with row-level visuals a native TreeView cannot render

DESIGN §Components (sidebar-tree-item); EXPERIENCE §IA
The tree wants selected-rail: 'inset 2px 0 0 {colors.accent}' (a 2px accent left rail on the active row) and a literal glyph set •/°/!/* as row markers. A TreeView gives TreeItem.label, .description (dim trailing text), .iconPath/ThemeIcon, .collapsibleState (free twisties), and a FileDecorationProvider (1–2 char colored badge + tooltip). It does not expose the row's selection background; you cannot paint a custom left-accent rail or style the active row — active-selection fill is the theme's list.activeSelectionBackground, full stop.
Fix: explicitly choose native TreeView and drop the 2px rail (accept VS Code's native selection highlight; keep the rail as a web-only delta), OR state the sidebar is a custom WebviewView if pixel control is required — and accept it forfeits free twisties, native keyboard tree-nav, and drag/drop, all of which you'd reimplement.
high

Count badges assume multi-digit numbers the platform won't render

DESIGN unread-badge; EXPERIENCE §IA
The wireframe shows 2 on #calling-interface and unread-badge is a "Source-Control-style count decoration." On a native TreeView that count can only come from FileDecoration.badge, which is hard-capped at 2 characters (VS Code source rejects longer badges). So 12 works, 137 does not — the SCM-style behavior actually truncates/omits over its limit. The pill shape ({rounded.full}) is web-only — a native badge is not pill-styleable.
Fix: cap displayed counts at "99" / use a non-numeric • activity dot beyond a threshold (and say so), or move the count into TreeItem.description (trailing dim · 137, no 2-char limit but renders as right-of-label dim text, not a pill).
medium

"Rooms open as editor tabs" asserts behavior without the WebviewPanel lifecycle costs

DESIGN room-tab note; EXPERIENCE §IA, Responsive
One WebviewPanel per room is correct, but: (a) a hidden panel is torn down unless retainContextWhenHidden: true, which holds the full DOM/JS in memory for every backgrounded room — N× and unbounded under "many tabs open"; (b) the unread •-on-a-background-tab needs retained context or a WebviewPanelSerializer to survive reload; (c) tab title/icon are set via panel.title/panel.iconPath and the leading-•/trailing-× treatment is partly host-owned — VS Code draws the ×, so the webview cannot style it.
Fix: state the per-room-WebviewPanel model explicitly, pick a retain-context policy (retain active + a small LRU, accept fast re-render on refocus for the rest), and note tab chrome is host-rendered — the •/× styling applies to web; on VS Code, unread is best signaled by a title-prefix character or the tab icon.
medium

border mapped to panel.border — not a general-purpose hairline

DESIGN §Colors table, row border
panel.border is specifically the divider between the editor area and the bottom panel (Output/Terminal) — frequently unset/transparent in many themes. Using it for every 1px divider, code-block border, and table border (the design leans "flat, border-led") yields invisible/inconsistent borders. contrastBorder is set only in high-contrast themes — a great additive HC guard but a non-answer in normal themes.
Fix: for general hairlines prefer a token that exists per-theme — --vscode-widget-border, or surface-specific --vscode-editorGroup-border / sideBarSectionHeader-border / input-border — and keep contrastBorder layered for HC. Audit each border use-site.
medium

High-contrast theme kind essentially unaddressed

EXPERIENCE §Accessibility Floor; DESIGN §Colors
The floor defers contrast to "the user's VS Code theme" and cites contrastBorder, but neither spine acknowledges the high-contrast theme kinds (HighContrast / HighContrastLight, via body.vscode-high-contrast(-light) / ColorThemeKind). The two functional brand colors — agreed-green and flag-warm — are literal hex on both surfaces (the per-surface table only remaps neutral/accent roles), so in HC they can fail the contrast contract the floor leans on, and a 0.07-alpha green wash is effectively invisible on an HC background.
Fix: name HC as a supported theme kind in Responsive & Platform; map agreed-green/flag-warm to charted tokens on the VS Code surface (--vscode-charts-green/-yellow, list.warningForeground, gitDecoration.*) rather than literals; gate alpha washes/left-rules behind a non-HC check (prefer a solid border to a translucent wash in HC).
low

Inert markdown is CSP-friendly only if the rendering path is committed

EXPERIENCE §Message post; DESIGN
CSP forbids inline script by default; "no script, code as text, safe links" is easier under CSP, not in tension — provided markdown renders to sanitized HTML (no event handlers, no javascript:/data: hrefs; links via the host) and syntax highlighting is precomputed to static <span class> markup, not an in-webview highlighter needing unsafe-inline/unsafe-eval. The restrained code tints imply a highlighter.
Fix: add one line: markdown → sanitized static HTML + class-based (pre-tokenized) highlighting, served under a strict CSP with ${cspSource} + a nonce; no inline/eval.
low

"Full parity" over-claimed on dimensions VS Code controls

EXPERIENCE §Foundation ("Multi-surface, full parity"); Responsive
The design mostly hedges ("the sidebar's width is the editor's, not ours") — good — but spacing.sidebar-w: 232px and the fixed-frame layout are web-only: on the extension surface you cannot force a 232px sidebar (the user drags it; it can be 120px or 600px, top/bottom, or moved to the panel/secondary side bar), the tab strip is host-rendered, and the font is whatever the user set.
Fix: reframe the headline as "behavioral parity, host-native chrome" rather than "full parity," and add a short "what does NOT carry to VS Code" note (fixed sidebar width, custom tab chrome, brand hex palette, pill badges, active-row rail).
