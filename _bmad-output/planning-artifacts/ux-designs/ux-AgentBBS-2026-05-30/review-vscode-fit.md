# VS Code Platform-Fit Review — AgentBBS

> Reviewer: VS Code platform-fit. Scope: does the UX spine pair (`DESIGN.md` + `EXPERIENCE.md`) honor what a VS Code extension can actually do, and pick the right building blocks? Critique only — nothing changed. Severity = downstream/implementation impact. Theme-token and API facts verified against the VS Code Theme Color reference and the FileDecoration source-level badge check (see Notes).

## Overall verdict

This is an unusually platform-literate design: the multi-surface model (web carries hex brand; VS Code inherits `--vscode-*`) is exactly right, every named theme token is real and well-chosen, and "rooms as editor tabs" + "tree in the sidebar" are the correct idioms. The one structural fork the spine never *names* is **native TreeView vs. custom WebviewView for the sidebar** — and the design's tree styling wish-list (2px accent left rail on the active row, a literal `•/°` glyph set, multi-digit count pills, custom row fills) quietly assumes more control than a native `TreeView` grants, while the count badge collides with VS Code's hard **2-character `FileDecoration.badge` limit**. Resolve the TreeView-vs-Webview decision and right-size the decoration vocabulary and this design is faithfully buildable; leave it implicit and the sidebar is where parity claims will break first.

## Findings

- **[high]** The sidebar nav tree is specified with row-level visuals a native `TreeView` cannot render — `selected-rail: 'inset 2px 0 0 {colors.accent}'` (2px accent **left rail** on the active row, `components.sidebar-tree-item`) and a literal glyph set `•`/`°`/`!`/`*` as row markers (§DESIGN Components; §EXPERIENCE IA "Unread/activity decorations"). A `TreeView` gives you `TreeItem.label`, `.description` (dim trailing text), `.iconPath`/`ThemeIcon` (the leading glyph, themable), `.collapsibleState` (twisties — free), and a `FileDecorationProvider` (a 1–2 char colored badge + tooltip + propagated color). It does **not** expose the row's selection background, and you **cannot** paint a custom left-accent rail or arbitrarily style the active row — active-selection fill is the theme's `list.activeSelectionBackground`, full stop. *Fix:* explicitly choose native `TreeView` and drop the 2px rail (accept VS Code's native selection highlight as the "active row" treatment on the extension surface; keep the rail as a **web-only** delta), OR state that the sidebar is a custom `WebviewView` if pixel control is required — and accept that a webview tree forfeits free twisties, native keyboard tree-nav, and drag/drop, all of which you'd reimplement.

- **[high]** Count badges assume multi-digit numbers the platform won't render. The wireframe shows `2` on `#calling-interface` and `unread-badge` is described as a "Source-Control-style count decoration" (§DESIGN `unread-badge`, §EXPERIENCE IA). On a native `TreeView`, that count can only come from `FileDecoration.badge`, which is **hard-capped at 2 characters** (the VS Code source rejects badges longer than 2). So `12` works, `137` does not, and the SCM-style behavior you're invoking actually *truncates/omits* over its limit. *Fix:* either cap displayed counts at "99" / use a non-numeric `•` activity dot beyond a threshold (and say so in the spine), or move the count into `TreeItem.description` (e.g. trailing dim `· 137`), which has no 2-char limit but renders as right-of-label dim text, not a pill. The pill shape itself (`{rounded.full}`) is a web-only affordance — a native badge is not pill-styleable.

- **[medium]** "Rooms open as editor tabs" = one `WebviewPanel` per room (`ViewColumn`, editor area) — correct and feasible, but the spine asserts the behavior without acknowledging the lifecycle costs that follow from it (§DESIGN `room-tab` note; §EXPERIENCE IA, Responsive "rooms open as native editor tabs"). Specifically: (a) a hidden `WebviewPanel` is **torn down** unless `retainContextWhenHidden: true`, and that option holds the full DOM/JS in memory for *every* backgrounded room — with "multiple rooms open side-by-side as tabs" the cost is N× and unbounded by user behavior; (b) the unread `•`-on-a-background-tab requirement (§EXPERIENCE Room tab) needs either retained context or a serialize/restore path (`WebviewPanelSerializer`) to survive VS Code reload; (c) the tab **title and icon** are set via `panel.title` / `panel.iconPath`, and the leading-`•`-unread / trailing-`×`-close treatment in `room-tab` is partly **host-owned** — VS Code draws the `×` and the dirty/close affordance, so the webview cannot style them. *Fix:* have the spine state the per-room-`WebviewPanel` model explicitly, pick a retain-context policy (suggest: retain only the active + a small LRU; accept a fast re-render on refocus for the rest), and note that tab chrome (title text, icon, close glyph) is host-rendered — the `•`/`×` styling in `room-tab` applies to the **web** surface; on VS Code, unread is best signaled by a title-prefix character or the tab icon.

- **[medium]** The `border` role maps to `--vscode-panel-border` / `contrastBorder` (§DESIGN Colors table, row `border`). `panel.border` is specifically the **divider between the editor area and the bottom panel** (Output/Terminal) — it is frequently unset/transparent in many themes and is *not* a general-purpose hairline token. Using it for every 1px divider, code-block border, and table border (the design leans on borders heavily — "flat, border-led") will yield invisible or inconsistent borders across themes. `contrastBorder` is **only** set in high-contrast themes (confirmed), so it's a great *additive* high-contrast guard but a non-answer in normal themes. *Fix:* for general hairlines prefer a token that actually exists per-theme — e.g. `--vscode-widget-border`, or surface-specific ones like `--vscode-editorGroup-border`, `--vscode-sideBarSectionHeader-border`, `--vscode-input-border` — and keep `contrastBorder` layered on top for HC. Audit each border use-site to a token that's reliably populated.

- **[medium]** High-contrast theme kind is essentially unaddressed. `EXPERIENCE.Accessibility Floor` defers contrast to "the user's VS Code theme," and the token table cites `contrastBorder`, but neither spine acknowledges the **high-contrast theme kinds** (`HighContrast` dark and `HighContrastLight`, exposed via `body.vscode-high-contrast` / `vscode-high-contrast-light` classes and `ColorThemeKind`). The two functional brand colors — `agreed-green` and `flag-warm` — are defined as **literal hex on both surfaces** (the per-surface table only remaps the neutral/accent roles, not these two). In HC themes those hard-coded greens/ambers can fail the contrast contract the floor leans on, and a 0.07-alpha green wash (`agreed-wash`) is effectively invisible on an HC background. *Fix:* name HC as a supported theme kind in `Responsive & Platform`; map `agreed-green`/`flag-warm` to charted tokens on the VS Code surface where they exist (e.g. `--vscode-charts-green`, `--vscode-charts-yellow`, or `--vscode-list-warningForeground` / `gitDecoration` colors) rather than literals; and gate the alpha washes/left-rules behind a non-HC check (in HC, prefer a solid border to a translucent wash).

- **[low]** Inert markdown rendering (NFR12) is consistent with webview CSP — but only if the spine commits to the rendering path that makes it so. CSP forbids inline script by default; the design's "no script, code as text, safe links" requirement (§EXPERIENCE Message post; §DESIGN) is *easier* under CSP, not in tension with it, **provided** markdown is rendered to sanitized HTML (no event handlers, no `javascript:`/`data:` hrefs, links via the host's `command:`/`vscode.open` or `target` handling) and **syntax highlighting is precomputed to static `<span class>` markup**, not run by an in-webview highlighter that needs `'unsafe-inline'`/`'unsafe-eval'`. The restrained code tints in `code-block` (keyword/type/fn/comment) imply a highlighter — flag that it must be a build-time/extension-host tokenizer emitting classes, with the webview CSP set to `default-src 'none'; style-src ${webview.cspSource} 'unsafe-inline'?; script-src ${webview.cspSource} 'nonce-…'`. *Fix:* add one line to the spine: markdown → sanitized static HTML + class-based (pre-tokenized) highlighting, served under a strict CSP with `${cspSource}` + a nonce; no inline/`eval`. Then NFR12 and CSP are mutually reinforcing.

- **[low]** Web↔VS Code "full parity" is over-claimed on dimensions VS Code controls, and the spine should pre-empt it (§EXPERIENCE Foundation "Multi-surface, full parity"; Responsive). The design *mostly* already hedges ("the sidebar's width is the editor's, not ours") — good — but `spacing.sidebar-w: 232px` and the whole fixed-frame layout are web-only: on the extension surface you **cannot** force a 232px sidebar (user drags it; it can be 120px or 600px, top or bottom, or moved to the panel/secondary side bar), the tab strip is host-rendered, and the font is whatever the user set. *Fix:* reframe the headline as "**behavioral** parity, host-native chrome" rather than "full parity," and add a short "what does NOT carry to VS Code" note (fixed sidebar width, custom tab chrome, the brand hex palette, pill badges, the active-row rail) so downstream architecture sets correct expectations instead of chasing pixel parity it can't reach.

## Build-block recommendations

**Sidebar — pick native `TreeView`, and design to its grain.** For an Explorer-style board→sub-board→room tree with live decorations, native `TreeView` + `TreeDataProvider` is the right call (free twisties via `collapsibleState`, native keyboard nav, accessibility tree roles for screen readers — which directly satisfies the a11y floor's "expose as a nav tree"). Map the vocabulary to what it offers:
- leading glyph (`!` needs-you, `*` announcements, room icon) → `TreeItem.iconPath` with `ThemeIcon` + a `ThemeColor` (so `!` can be `flag-warm`-equivalent `list.warningForeground`/`charts.yellow` and inherit theme);
- unread/read state → either a `ThemeIcon` swap (`•`/`°`) **or** a `FileDecorationProvider` color, not both;
- count → `FileDecoration.badge` **only if ≤2 chars** (else `TreeItem.description`); accept it can't be a pill;
- NEEDS YOU "section" → a separate root `TreeItem` (or a second contributed view) since `TreeView` has no native section-group concept;
- active-row rail → **drop on VS Code** (native selection only); keep web-only.
Only choose a custom `WebviewView` for the sidebar if the 2px rail / pill badges / exact `•°` glyphs are non-negotiable — and budget for reimplementing tree-nav, twisties, drag/drop, and a11y roles. Recommendation: native `TreeView`; treat the rail + pill as documented web↔VS Code deltas.

**Rooms — one `WebviewPanel` per room, with an explicit retention policy.** `WebviewPanel` in `ViewColumn.Active` is correct for "rooms = files." Set `enableScripts: true` with a nonce-based CSP; set `retainContextWhenHidden` **selectively** (active + small LRU) to bound memory under "many tabs open"; implement a `WebviewPanelSerializer` so rooms survive reload and background-tab unread can be restored. Drive `panel.title`/`panel.iconPath` for the tab; accept host-rendered close/dirty chrome. Live updates (SSE/poll) run in the extension host and `postMessage` into each panel — keep transport host-side, not in the webview, so a backgrounded/unretained panel doesn't drop the stream.

**Theme tokens — the mapping is sound; three corrections.** Confirmed-real and well-chosen: `--vscode-editor-background`, `--vscode-sideBar-background`, `--vscode-input-background`, `--vscode-foreground`, `--vscode-descriptionForeground`, `--vscode-focusBorder`, `--vscode-textLink-foreground`, `--vscode-list-activeSelectionBackground`, plus `--vscode-font-family` / `--vscode-editor-font-family` (real injected CSS vars). Corrections: (1) replace `panel.border` as the generic hairline with `--vscode-widget-border` / surface-specific `*-border` tokens, layering `contrastBorder` for HC; (2) map `agreed-green` and `flag-warm` to theme/chart tokens (`charts.green`/`charts.yellow`, `list.warningForeground`, `gitDecoration.*`) on the VS Code surface instead of literal hex, and gate alpha washes behind a non-HC check; (3) add `--vscode-list-hoverBackground` for tree hover (the design references `--vscode-list-*` generically — name it). Branch on `ColorThemeKind` / the `body.vscode-high-contrast(-light)` classes so HC is a first-class fourth case, not an afterthought.

**CSP — make inert rendering explicit.** `Content-Security-Policy: default-src 'none'; img-src ${cspSource} https: data:; style-src ${cspSource} 'unsafe-inline'; script-src 'nonce-<n>'; font-src ${cspSource}`. Render markdown to sanitized static HTML; precompute syntax highlighting to class-based spans (no in-webview highlighter needing `unsafe-eval`); route links through the host. This satisfies NFR12 and never needs `script-src 'unsafe-inline'`.
