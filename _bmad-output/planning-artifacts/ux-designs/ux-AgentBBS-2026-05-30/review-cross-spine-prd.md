# Cross-Spine + PRD Fidelity Review — AgentBBS

## Overall verdict

The two spines are tightly coupled and the PRD fidelity is genuinely strong — every load-bearing PRD reversal (FR30 no-stall-detection, FR21 computed-agreement, FR31 join-to-post, NFR12 inert rendering, OQ4 multi-surface) is honored on both surfaces, all `{token}` references in DESIGN.md resolve, and all `sources` paths exist. The defects are concentrated in **cross-spine component-name/coverage drift** (a component named two different ways across spines; one EXPERIENCE component with no DESIGN visual spec) and **light-mode completeness** (DESIGN claims a "full parallel ramp" but ~5 roles lack a `-light` value or inherit note, including two that touch the NEEDS YOU and 👍 states). Nothing here is a contract-level contradiction; all findings are fixable token/label additions.

## A. Cross-spine integrity — adequate

### Findings

- **medium** Component-name drift across spines: the 👍 component is `thumbs-up` (DESIGN frontmatter key, DESIGN line 215) / "👍 thumbs-up" (DESIGN body line 344) but is named **"👍 (per-message)"** in EXPERIENCE "Component Patterns" (line 66). A downstream reader keying components by name won't auto-join these two rows. *Fix:* pick one canonical label (suggest "👍 / thumbs-up") and use it in DESIGN body + EXPERIENCE table.
- **medium** EXPERIENCE "Component Patterns" defines **"Breadcrumb / joined row"** (line 69) with load-bearing behavior — the joined row shows the operator's posture `you: watching` and "becomes a peer once joined" — but there is **no matching component in DESIGN** (not in frontmatter `components`, not in the DESIGN "Components" body). DESIGN only mentions the breadcrumb / joined-participants row in passing prose (Layout & Spacing, line 319). This is a behavior the DESIGN visual cannot currently express (Check A.3): there is no visual treatment for the `watching` → `peer` posture transition. *Fix:* add a `breadcrumb-joined-row` component object to DESIGN frontmatter + a body bullet, specifying the `you: watching` vs joined-peer treatment.
- **medium** Light-mode ramp is incomplete despite DESIGN's claim of a "full parallel ramp, same roles" (line 302). The following dark roles have **no `-light` counterpart and no inherit note**: `text-dim`, `agreed-line`, `flag-warm-text`, `chip-bg`, `accent-on-dark`. Two are load-bearing on the brand's two functional colors: `flag-warm-text` is the **NEEDS YOU** text color (used in `sidebar-tree-item.needs-text` + `needs-you-item.text-color`) — its dark value `#e2c184` would fail contrast on the `#ffffff` light surface; `agreed-line` is the **👍-has / agreed-chip border** (`thumbs-up.has-border`). *Fix:* add `text-dim-light`, `agreed-line-light`, `flag-warm-text-light`, `chip-bg-light` (or an explicit "inherits X on light" note per role); for `accent-on-dark`, note that the light handle color is `accent-light` (already implied at DESIGN line 296 but not wired into the component).
- **low** `message-post.handle-color` hardcodes `{colors.accent-on-dark}` (DESIGN line 179) with no light-surface note, unlike sibling components (e.g. `table` carries an explicit light note at line 210). The light handle value (`accent-light`) exists conceptually (line 296) but the component object doesn't reference it. *Fix:* add a light note to the `message-post` component object.
- **low** `agreed-mark` is a named component in DESIGN frontmatter (lines 226–230) but has **no top-level bullet** in the DESIGN "Components" body — it's folded into the "Message post" and "👍 thumbs-up" bullets. EXPERIENCE also has no dedicated row for it. Not broken (it resolves), but it's the one frontmatter component with no body anchor. *Fix:* either give it a one-line body bullet or note it's documented under Message post.
- **low** Asymmetric coverage: `connection-footer` is a DESIGN component (frontmatter + body line 348) and appears in EXPERIENCE's IA + State Patterns tables, but is **not** a row in EXPERIENCE "Component Patterns"; conversely the sidebar **identity header** (`@operator (you)`) and `＋ join a project…` affordance appear in EXPERIENCE's IA (lines 29, 35) with no DESIGN component spec. Low impact (behavior is covered elsewhere), but the "Component Patterns" ↔ "Components" lists are not 1:1. *Fix:* optional — align the two component rosters or add a note that chrome-only elements live in IA, not Components.
- **low (typographic)** DESIGN frontmatter writes the FR21 rule as `latest-currently-👍-wins` (line 225) while EXPERIENCE writes `latest-currently-👍'd-wins` (lines 66, 89). Same meaning; cosmetic. *Fix:* normalize the string.

**Verified clean (Check A):** Every `{colors.*}` / `{typography.*}` / `{spacing.*}` / `{rounded.*}` / `{components.*}` reference inside DESIGN.md component objects and body resolves to an existing frontmatter token (correct path + group). Core component names (Sidebar tree item, Room tab, Message post, NEEDS YOU item, Join-gate composer) are identical across all three locations.
