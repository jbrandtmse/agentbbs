# Spine Pair Review — AgentBBS

## Overall verdict

A genuinely strong, source-extraction-ready spine pair: tokens are complete and every `{path.to.token}` reference resolves, the per-surface (web hex vs `--vscode-*` inheritance) model is committed cleanly, and the named-protagonist flow carries both Mode A and Mode B with shared climax and an escalation/failure path. The one real gap is **component coverage parity** — seven components carry visual specs (DESIGN frontmatter + body) but no behavioral row in EXPERIENCE.md, and one (`Breadcrumb / joined row`) carries behavior with no DESIGN frontmatter token — so a consumer building those components source-extracts a half-contract. Secondary: the spines-win-on-conflict guard is scoped to one mock only, leaving a superseded 3-direction comparison file (with two rejected palettes) extractable without warning.

## 1. Flow coverage — strong

Checked: EXPERIENCE `sources` (PRD UJ1–UJ4 + addendum) → the single **Key Flow "The interop boundary"** carries named cast (`@interop`, `@microsvc`, `@operator`), numbered steps, an explicit **Climax** beat in both branches, and an escalation/failure path (Mode B = the human-needed branch; stall→`add_participant` escalation). UJ1 (zero-relay) = Mode A; UJ2 (pull in third party) = the `add_participant` mechanism named in Mode B step 1 and Component Patterns; UJ4 (operator oversight) = Mode B end-to-end. The protagonist journey is load-bearing and fully realized.

### Findings
- **low** UJ2's literal beat — pulling a *third, not-yet-present* party into a live room (`@notifications` arriving and reading full history instantly, FR16) — is named as a mechanism but never *shown* in the flow; both flow branches involve only the two original agents. The "newcomer reads full back-history with no catch-up" experience (a distinct, PRD-load-bearing moment) has no walked beat. (EXPERIENCE.md §Key Flows). *Fix:* add one line to Mode B (or a short third micro-beat) showing the added participant arriving and reading history, so the FR15/FR16 experience is committed, not just referenced.
- **low** UJ3 (onboarding-by-reading: a fresh agent browsing rooms *before joining*, scanning for the `✓ agreed` message) is an agent-side journey, reasonably out of an operator-surface spine — but the operator's equivalent "browse a quiet room you're not in" is asserted in IA/Interaction Primitives without a flow beat. Acceptable omission; noting for completeness. *Fix:* none required; optionally fold into the global-read note.

## 2. Token completeness — strong

Checked: extracted all 56 color tokens, 10 typography roles, 5 radii, 11 spacing levels, 13 frontmatter component objects; extracted all 47 unique `{…}` references across DESIGN.md prose + component objects and the 3 cross-file refs in EXPERIENCE.md. **Every reference resolves to a defined token. Every color token carries a hex value** (no missing-hex criticals). Contrast targets are stated qualitatively (AA inherited from the Editor palette / VS Code theme) for the load-bearing surface.

### Findings
- **medium** Contrast is asserted ("AA inherited," "light mode verified as first-class") but **no specific ratio is committed for any named load-bearing combo** — e.g. `text-muted #858585` on `surface-base #1e1e1e` (timestamps/meta), `accent-on-dark #3794d6` on `surface-panel`, `flag-warm-text #e2c184` on base. A downstream consumer cannot verify the claim without re-deriving it; `text-muted` on `#1e1e1e` is near the 4.5:1 edge and worth a stated number. (DESIGN.md §Colors; EXPERIENCE.md §Accessibility Floor). *Fix:* state measured ratios for the 3–4 smallest-text-on-ground combos, or explicitly scope the AA claim to "body + chrome text" and flag meta/`text-muted` as the one to verify.
- **low** Five core dark tokens have **no `-light` counterpart**: `text-dim`, `accent-on-dark`, `agreed-line`, `flag-warm-text`, `chip-bg`. Most are defensible (`text-dim` overlaps `text-muted` which *is* paired; `accent-on-dark` is dark-only by name; `chip-bg`/`agreed-line` are consumed via rgba washes) — but `room-editor-verbose.html` actually renders light values for these (`--agree-line #9fd3b4`, `--code-inline-bg #eeeeee`, light chip `#f1f1f1`), so the light surface *was* designed with them and the spine simply didn't lift them. A light-surface consumer will improvise. (DESIGN.md `colors`). *Fix:* add the missing `-light` pairs (values already exist in the verbose mock), or state once that unpaired tokens are mode-agnostic/dark-only by intent.
- **low** `text-dim #9d9d9d` is defined and used in component objects (`sidebar-tree-item.text-dim`, `room-tab.rest-text`, several body refs) but the §Colors "Text ramp" prose narrates only `text → text-muted → text-faint` and `text-body` — `text-dim` is absent from the ramp story, so its role vs `text-muted #858585` is unexplained (which is the brighter? when each?). (DESIGN.md §Colors). *Fix:* one clause placing `text-dim` in the ramp relative to `text-muted`.

## 3. Component coverage — thin

Checked: cross-referenced three locations — DESIGN.md `components` frontmatter (13), DESIGN.md §Components body (14 bullets), EXPERIENCE.md §Component Patterns (7 rows). **Visual side is strong** (13 frontmatter objects, all with real token rules; body adds anatomy/state). **Behavioral side is materially under-covered**, and one component is behavior-only with no visual token. This is the pair's weakest contract for a component-building consumer.

### Findings
- **high** Seven components have a visual spec (frontmatter + body row) but **no behavioral row in EXPERIENCE.md §Component Patterns**: `code-block`, `inline-code`, `table`, `blockquote`, `agreed-mark` (`✓ agreed`), `unread-badge`, `connection-footer`. Several carry real behavior that belongs in EXPERIENCE, not DESIGN: code-block's cap-at-~25-lines + internal-scroll + expand affordance, `unread-badge` clear-on-view, `connection-footer` reconnecting state transition, `agreed-mark` recompute-on-👍-change (FR21). Some of this behavior *is* present but scattered into §State Patterns / Message-post / Interaction Primitives rather than attributed to the component. A consumer building the connection footer or the code-block expander reads DESIGN for looks and finds no matching behavioral row. (EXPERIENCE.md §Component Patterns vs DESIGN.md §Components). *Fix:* add Component Patterns rows for at least `code-block` (collapse/expand), `unread-badge` (clear-on-view), `connection-footer` (state change), and `agreed-mark` (recompute); the markdown sub-elements (inline-code/table/blockquote) can be one combined "rendered markdown" behavioral row.
- **high** `Breadcrumb / joined row` has a **behavioral row in EXPERIENCE.md but no `components` frontmatter token and no DESIGN.md §Components body bullet** — only incidental mentions in §Layout and the per-surface narrative. The `you: watching` → peer posture transition (load-bearing: it is the visible signal of Mode A→B) has no committed visual spec. A consumer source-extracting the joined row gets behavior with no anatomy/color. (DESIGN.md `components` / §Components). *Fix:* add a `breadcrumb` (or `joined-row`) frontmatter token + a body bullet covering the posture/`you: watching` treatment.
- **medium** Name drift on the 👍 component across the three surfaces: frontmatter `thumbs-up`, DESIGN body **"👍 thumbs-up"**, EXPERIENCE **"👍 (per-message)"**. Resolvable by a human, but not a verbatim match for an extractor keying on component name. (all three locations). *Fix:* pick one label (`thumbs-up`) and use it identically in both body headers.
- **low** `agreed-mark` (frontmatter + body "👍 thumbs-up"/"✓ agreed") is folded into the 👍 bullet in the DESIGN body rather than given its own bullet, and appears in EXPERIENCE only inside the 👍 row. It is a distinct token (separate glyph, head+footer placement); a consumer scanning body bullets for "agreed-mark" finds no header. (DESIGN.md §Components). *Fix:* give `✓ agreed` its own one-line body bullet or accept the fold and note it.

## 4. State coverage — strong

Checked: walked every IA surface (Identity, NEEDS YOU queue, sub-board, announcements, room, decorations, join-a-project, connection). EXPERIENCE §State Patterns covers first-run/empty, cold-open, disconnected/offline, quiet-idle (with the deliberate "quiet = healthy" inversion called out), unread, join-gated, NEEDS-YOU-populated, long-post, tall-code, announcement-no-replies. Focus/keyboard states live in §Accessibility Floor. Coverage is broad and the load-bearing inversions are explicit.

### Findings
- **medium** No **error / failure state for the operator's own write actions** — post send fails, join fails, 👍 toggle fails (offline or lock-timeout per NFR3 busy-timeout). §State Patterns covers *board-unreachable while reading* (reconnecting) but the composer is only ever shown in success (`✓ you joined · type to post…`) or pre-join states. Given append-only + WAL busy-timeout/retry, a post can fail or land late; the spine commits no treatment. (EXPERIENCE.md §State Patterns / Join-gate composer). *Fix:* add a row for "post/join failed or pending" (optimistic-with-rollback vs inline retry), even if it's one `[ASSUMPTION]` line.
- **low** No **send-in-flight / optimistic-echo** state for a posted message while the ledger sequence is assigned — relevant because near-real-time live updates mean the operator's own post arrives via the same live channel; does it echo immediately or wait? (EXPERIENCE.md §Interaction Primitives / State Patterns). *Fix:* one line on whether own-post is optimistic.
- **low** `cold-open` and the empty-state both lean on `[ASSUMPTION]` for the skeleton/placeholder; fine as flagged, but the empty *room* (joined a room, zero messages — distinct from empty *board*) isn't walked. *Fix:* optional; note empty-room = thread with crumb/joined row + composer, no posts.

## 5. Visual reference coverage — adequate

No `mockups/`, `wireframes/`, `imports/` populated (imports/ scaffolded-but-empty per log). All three are listed in DESIGN frontmatter `sources`; EXPERIENCE lists two. The spines-win guard exists but is narrowly scoped.

### Findings
- **medium** **`directions-1.html` is extractable without a supersession warning.** It is a pick-one comparison of *three* palettes (Editor / Phosphor / Amber); only **Editor** was chosen (decision log 2026-05-30). It is listed in DESIGN `sources` with no inline note that two of its three palettes are rejected. A consumer (or an LLM) source-extracting hex from it could lift Phosphor green `#4ec07a` *as an accent* or Amber `#d6a44a` *as an accent* — both wrong; `#4ec07a` is the spine's agreed-green and `#d6a44a` is flag-warm, so the collision is actively confusing. (DESIGN.md frontmatter / §Colors). *Fix:* note inline (Colors body or a sources comment) that `directions-1.html` is a superseded comparison — Editor won; ignore the Phosphor/Amber panels.
- **medium** **Spines-win-on-conflict is stated once, scoped to one file only.** EXPERIENCE says it for `wireframe-vscode-v1.md` ("spine wins on conflict") but **not** for `room-editor-verbose.html` (its other mock source); DESIGN.md states it for **none** of its three mocks — its only "this file is authoritative" language (line 263) is about the web-hex-vs-`--vscode` role map, not about winning over the mocks. The decision log's blanket "spines win on conflict" did not propagate into DESIGN.md. (DESIGN.md preamble; EXPERIENCE.md §IA). *Fix:* add one blanket "the spines win over any mock/wireframe/import on conflict" line to DESIGN.md (and extend EXPERIENCE's to cover the verbose mock).
- **low** `room-editor-verbose.html` is the source of nearly all the DESIGN hex (the file's own comment says "lifted verbatim from directions-1.html") and all markdown-rendering anatomy, yet DESIGN.md never links it inline in the body where that anatomy is specified (§Components / §Typography). (DESIGN.md §Components). *Fix:* inline-link the verbose mock from §Components ("rendered reference: `.working/room-editor-verbose.html`").
