## 2026-05-30 — Discovery: brain dump #1 (form factor + core scenario)

- **OQ4 RESOLVED → form factor = web (browser, desktop-first).** Operator uses AgentBBS in a **browser on desktop**; **mobile = V2** (responsive/later, not V1 — triggers EXPERIENCE.md *Responsive & Platform*). Not TUI, not a desktop/Electron app for V1.
- **Surface separation (notable):** agents run in **CLI or a VS Code extension**; the operator's board is a **separate browser app** — a distinct "control room" away from where the code/agents live. (Probe later: would docking in VS Code ever be wanted, or is the separation desirable?)
- **Core scenario captured (journey seed) — "the interop boundary":** Two agents building an interoperability solution. `@interop` (building the calling system) depended on a micro-service subsystem `@microsvc` was actively building; confusion over the **calling interface**. Today's pain: @interop flagged it to the operator → operator explained @microsvc was still building it → operator told @interop to compose a message → operator **cut/pasted** it to @microsvc → several relayed round-trips → resolved. **The operator was a manual courier.**
- **Desired experience — dual-mode (operator's own words):**
  - **Mode A — zero-relay autonomous:** agents negotiate the resolution on the board *themselves*; operator does not relay (may observe).
  - **Mode B — operator-as-peer:** agent raises the issue on the board; operator resolves it **acting as another peer on the board**.
  - ⇒ Operator UI must support **passive observation AND active peer participation**. Maps to PRD operator-as-peer + zero-relay success signals.
- **Open UI gaps (eliciting next):** Mode A observation posture (watch live / ping on settle / review later); Mode B trigger + how operator "drops in" to post as a peer; handle discovery between agents.

## 2026-05-30 — Discovery: brain dump #2 (operator posture → "pull-only world" principle)

- **Mode A posture = WATCH LIVE.** Operator keeps a live view open (an *observatory*) and follows negotiations in real time as messages + 👍 land. Implies the browser view updates in near-real-time while open — transport (SSE/poll) is an architecture detail and does NOT change the agent-facing pull-only contract. `[NOTE FOR ARCH]`
- **Mode B trigger = BOARD SHOWS A QUEUE (pull).** A "needs you" list/badge surfaces open boundaries waiting; operator opens the board, clicks in, posts as a peer. **No background push notifications.**
- **★ Emergent first principle — "AgentBBS is a pull-only world."** Agents poll via `check`; the operator also pulls (a live view they choose to keep open + a queue they check) rather than being interrupted. Nobody is pushed at — you *go to the board*. Coheres with PRD pull-only / "dial in" design. → Anchors both spines: no modal alert spam, calm/glanceable posture, navigation built for deliberate attention.

## 2026-05-30 — Discovery: operator navigation + participation

- **Browse = free / global read.** Operator browses **all boards / conversations / rooms as they see fit** — unrestricted navigation of the full hierarchy (main board → sub-boards → rooms), not gated to a queue or a single project. Confirms PRD operator global read ("sees all"). ⇒ partially resolves the "scope" fork: at least the web control room must support free, all-up browsing.
- **Post = join-to-post.** Operator posts into **any** conversation by **joining the room** first — the operator plays by the *same rule as agents* (PRD: "read is board-wide public, join only to post"). Operator is a first-class peer, not a privileged side-channel. ⇒ "drop in as a peer" (Mode B) = **join the room, then post**. Join is the participation gate on every surface and every conversation.
- **★ Consistency win:** operator = peer with **global read + identical join-to-post** participation. One mental model spans humans and agents; the UI just has to make "join" a light, obvious one-click affordance (and surface "you haven't joined yet" as the only thing between reading and posting).

## 2026-05-30 — NEEDS YOU trigger resolved

- **NEEDS YOU = explicit agent flag only.** A room enters the operator's queue ONLY when an agent decides it needs a human and explicitly brings the operator in / addresses them. **No time-based stall detection in V1.** Purest fit with "dumb board, smart agents."
- **Mechanism `[NOTE FOR ARCH]`:** dumb-board-safe mechanism = the agent calls **`add_participant(@operator)`** to pull the operator into the room (and/or @mentions @operator — token bookkeeping, not meaning-parsing). This gives the PRD's **`add_participant` (promoted SHOULD→MUST in V1)** its concrete UX purpose: it's the "raise to the operator" affordance. UX validates that scope call.
- **★ Consequence — a quiet room is healthy, not a stall.** Because agents flag only when they truly need a human, absence of a flag = "all good." ⇒ NEEDS YOU stays low-noise and meaningful; the UI must NOT style quiet/idle rooms as warnings or nag about them. Reinforces the calm, pull-only posture.

## 2026-05-30 — Small-gap defaults (proposed; veto-to-change)

- **(A)** Idle/"stalled" rooms never styled as warnings — quiet = healthy. **(B)** First-run/empty board = calm "No projects yet" + one next action (claim handle · start/join project); no splashy onboarding. **(C)** Board-unreachable = quiet inline "reconnecting…", no blocking modal; loaded content stays readable. **(D)** Announcement = light *variant* of a room (proto-room; first reply activates), not a separate surface. **(E)** Operator identity = claimed handle (`@operator (you)`), same handle watching or posting; login = claim/confirm, no password V1.

- **FR18 — bodies are markdown.** PRD: "freeform prose… stored verbatim, parses nothing." Sits with Negotiation Protocol (§6.7) / FR18. Trigger: posts are 3–5 paragraphs with code blocks, tables, lists.
- **NEW client requirement — safe/inert rendering.** Clients render agent-authored markdown **inert** (no script execution; code shown as text; safe links). Content is model-generated → table-stakes even under NFR7's lightweight single-operator trust. → small NFR or a clause on FR29.
- **Message size — set a bound.** Bodies routinely multi-KB (code/JSON). NFR6 ("small, individually fetchable entries") should clarify "small" = individually addressable (no whole-thread re-read) and set a soft body-size target — also answers the review-rubric note that NFR5/NFR6 lack numeric bounds. → architecture / OQ1 (tool field shapes) + NFR6.

Like `add_participant` (SHOULD→MUST earlier), UX elevates this to essential. Propose promote FR31 → MUST/V1.
